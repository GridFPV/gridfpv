Doc Authoring Conventions

Internal · how we write these design docs

How the internal design docs are built — so every doc looks and behaves the same. These docs are hand-written HTML, read locally in a browser, and must render offline over file:// with no CDN and no build step.

The rules

Self-contained & offline. No web fonts, no CDN, no external requests. Everything a doc needs is vendored under assets/ and must work from a bare checkout opened as a file.

One shared stylesheet. Every doc links assets/style.css and uses its components — don't add per-page <style> blocks. Add reusable styling to the shared sheet instead.

House components. Reuse the existing building blocks: .masthead, .lead, .callout, .principle (with a .name span), .sim-note (with a .label span) for IRL/sim divergences, .tag (.required/.optional), dl.entities for data models, and ol.decisions for open questions.

Diagrams — Mermaid

Architecture and flow diagrams use Mermaid, rendered client-side from text. The Mermaid build is vendored at assets/vendor/mermaid.min.js (the classic-script build that exposes a window.mermaid global — the ES-module build will not load over file:// in Chrome). assets/diagrams.js initializes it with a theme matched to the brand palette and renders every <pre class="mermaid"> block on the page.

How to add a diagram

Author the diagram as a Mermaid code block:

flowchart LR
  a["Source"] -->|canonical events| b[("Append-only log")]
  b -->|derive| c["Projection"]
  c --> d["Client"]

…which is written in the page as:

<pre class="mermaid"> flowchart LR a["Source"] -->|canonical events| b[("Append-only log")] b -->|derive| c["Projection"] c --> d["Client"] </pre>

Then include the two scripts at the very end of <body>, in this order:

<script src="assets/vendor/mermaid.min.js"></script> <script src="assets/diagrams.js"></script>

Gotchas

  • For a line break inside a node label, write &lt;br/&gt; in the HTML source (HTML-escaped), so Mermaid receives the literal <br/> as text rather than the browser consuming it as a real element.
  • The raw source is hidden until Mermaid stamps data-processed on the block — so a diagram that fails to render shows nothing rather than raw text. If a diagram is blank, check the console for a Mermaid parse error.
  • Keep diagrams as text — never paste an exported image. The whole point is diffable, editable, offline-rendered diagrams.

Updating Mermaid: re-vendor by downloading the classic build (e.g. mermaid@<version>/dist/mermaid.min.js) over assets/vendor/mermaid.min.js and confirm it still ends with a globalThis["mermaid"] = … assignment (i.e. it's the global-exposing build, not the ESM one).
