Internal Design & Developer Docs

Internal documentation — not user-facing, not hosted.

The design and engineering record for GridFPV: the thinking behind the project and the decisions that guide the build.

These docs are for us — the people building GridFPV. They capture vision, architecture, and design rationale. They are written in HTML and read locally in a browser; we do not host them.

User-facing documentation (guides for race directors, pilots, and self-hosters) is a separate concern and will live in its own repository later. Keep that material out of this repo.

Authoritative, but living. These docs are the current plan of record — build against them, and treat their decisions as settled until deliberately changed. They are not sacred: keep questioning the choices, and when a better answer emerges or reality disagrees, update the document so it stays the source of truth. Each doc records its open decisions for exactly this reason. A plan we're afraid to revise stops being a useful plan.

Documents

  • Vision
    What GridFPV is and why it exists — the thesis, the design principles we won't violate, and how we sit in the landscape. The north star.
  • Event Pipeline
    What it means to run an event — the phases (setup, practice, qualifying, mains, season), the recurring heat loop, and the capabilities we want to hit at each one, for both IRL and Velocidrone racing.

Pipeline deep dives

  • Setup & Registration
    Defining the event (classes, track, format) and assembling a checked-in roster — intake paths, presence, and the data setup implies.
  • Practice
    Optional, event-wide, non-binding flying — rolling/scheduled/free-fly structures, a hot-lap board, and the timer-calibration window.
  • Qualifying
    Establishing the seeding ranking — run live, import, or skip; metrics, the shared rolling queue, and configurable round aggregation.
  • Brackets / Mains
    The competition proper — seed, generate the bracket, run and advance; win conditions, live marshaling, multi-class scheduling.
  • Championship / Season
    The cross-event layer — linking events into a season, configurable scoring, and the Director-local / Cloud-aggregate split.

Reference

Ordered the way the system is best understood and built: the map first, then the Director's core data path (timing in → engine → protocol out) and the clients that consume it, then the optional subsystems that hang off it, then how we keep it correct, and finally the plan that sequences the work.

  • Architecture
    System shape, the technology stack and why, the append-only spine, and the one-protocol/two-transports contract. The deep technical record — start here.
  • Timer Adapters
    The adapter interface and canonical event model — the foundational wall that makes every timing source (Velocidrone, RotorHazard, LapRF, manual) look the same to the engine. The vocabulary the whole log speaks.
  • Race Engine
    The heat loop, the pluggable bracket / qualifying generator registry, advancement, and multi-class scheduling — the competition machinery that consumes canonical events.
  • Protocol
    The single read/realtime contract both transports speak — snapshot, change stream, subscription scoping, auth, and versioning.
  • Clients
    The web client surfaces — RD console, racer/spectator PWA, and OBS overlays — the frontend framework choice, the shared component library, and PWA mechanics.
  • Cloud & Season
    The optional relay, long-term warehouse, and cross-event season layer — resumable push, the warehouse, season scoring, and identity reconciliation.
  • Streaming
    The broadcast subsystem — overlays as protocol clients, plus OBS control and the capture/RTMP boundary.
  • External Integrations
    MultiGP RaceSync (roster import, results push) and open data — the public read API, export, and embeddable widgets. The pilot owns their data.
  • Testing Strategy
    How we keep race-timing logic correct: pure translators, golden cases, recorded-session replay, and the guardrail against depending on a live shared backend.
  • Roadmap
    The release-versioned phase plan (v0.1 → v0.8) from foundations through the Director, Cloud, PWA, and integrations — and how it maps onto GitLab's free-tier planning features.
