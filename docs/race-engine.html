Race Engine

Internal design doc · the heat loop, the format registry, and how a race is run

The machinery that turns canonical passes plus a format into a run race. It consumes the passes the adapters produce, runs the heat loop, derives laps and results as projections, and advances per the format's rules until there's a result. The same loop powers Practice, Qualifying, and Mains — only the format differs.

This doc owns the heat loop, the format / generator interface, and how heats are scored and advanced. It defers the exact rules of each named format (MultiGP P9–P16, FAI, Chase-the-Ace, ZippyQ specifics) to per-format specs written as they're built; here we define the interface they plug into. It builds on canonical events from Timer Adapters and the append-only spine from Architecture §3. When this doc and the Vision disagree, the Vision wins.

1. Where it sits

The engine is the consumer between the timing layer and the projections. Passes arrive as canonical observations; the engine runs heats and appends race-state events (staged, armed, started, scored, advanced); laps, results, and standings are projections derived from the whole log. The engine holds race logic but never owns timing truth — it reacts to passes, it doesn't generate them.

2. The heat loop

One reusable state machine runs every heat, in every phase. Each transition is an appended race-state event, so a heat's whole history — including an abort or a re-run — is reconstructible from the log, and live race control is just commands that drive these transitions. 

stateDiagram-v2
  [*] --> Scheduled
  Scheduled --> Staged: stage
  Staged --> Armed: arm
  Armed --> Running: start
  Running --> Landed: time elapsed / all landed
  Landed --> Scored: score
  Scored --> [*]: advance
  Staged --> Scheduled: abort
  Armed --> Staged: abort
  Running --> Staged: abort / restart
  Scored --> Scheduled: discard & re-run

Passes are consumed only while a heat is Running (and during a grace window after — late crossings still count until the heat is scored). Staging is the countdown; arm opens the gate to detections; land closes the race; score finalizes the result; advance hands results to the format. Abort, restart, and discard-and-re-run are first-class transitions, recorded like any other.

IRLStaging assigns frequencies/channels and avoids conflicts; landing waits on marshals; re-runs are common.

SimNo frequency step; heats can fire back-to-back; staging is a short countdown.

3. The format / generator interface

Formats are a pluggable registry — the same idea as adapters, for competition structure. There is one unified generator interface, and qualifying formats and bracket formats are both implementations of it.

A format is a function of state, not a fixed schedule. Given the seeded field, its config, and the results of completed heats, a generator does three things: emit the next heat(s), or declare the format complete, and at any point expose the current ranking. That single contract drives the heat loop until a format finishes.

The honesty-forcing case is ZippyQ / rolling. It is not a precomputed bracket — the RD adds rounds on demand and pilots fly when ready. If the interface handles "produce more heats dynamically from current state," then fixed structures (round robin, single / double elimination, multi-tier A/B/C/D/E mains, Chase-the-Ace, MultiGP/FAI P9–P16) are the easy case — a generator that happens to emit a predetermined sequence. Designing against the dynamic format keeps the abstraction honest, exactly as Velocidrone does for adapters.

Qualifying and mains differ only in what their generators do internally: a qualifying generator runs rounds and aggregates flights into a ranking; a bracket generator emits heats and advances seeds toward a winner. Both emit heats, consume results, and expose an ordering — so the heat loop, scheduling, and advancement machinery are written once and shared.

4. Scoring & lap derivation

Scoring is shared engine logic over the canonical passes, so every source is scored identically. Passes become laps; laps and a win condition become a heat result.

  • Laps from passes. The first pass is the holeshot / start; a lap completes on each subsequent crossing of the lap gate (a full circuit of the gates / splits where the track has them). Marshaling adjudications (void, insert, adjust) fold in exactly as in Architecture §3 — the lap list is a projection.
  • Win condition (per-heat / format config). Most laps in a time window, first to N laps, or best single / consecutive lap (qualifying). The engine applies the configured condition; ties break by a recorded rule.

5. Advancement & scheduling

When a heat is scored, its result is handed to the format generator, which decides what comes next — more heats (with seeds advancing per the configured "top-N advance"), a move up a tier, a finals heat, or completion. This is the circular heart of the mains: run → result → advance → run.

Multi-class scheduling. Several classes can be live at once, each with its own format, sharing scarce resources — the timer and, for IRL, the frequency pool. The engine interleaves heats across classes and serializes access to shared resources; frequency allocation specifically is a contested ownership question (below).

Manual adjustments. Re-seeding, moving a pilot between heats before they fly, and discard-and-re-run are RD actions appended as events the generator respects on its next step — never edits to past truth.

6. Determinism & replay

The engine is a pure function of the log. Given the same events, it produces the same heats, results, and standings — that's what lets projections rebuild and recorded sessions replay (the testing backbone). Anything non-deterministic — a random draw for seeding, a coin-flip tie-break — is resolved once and its outcome recorded as an event, so replay never re-rolls it.

7. Open decisions

  1. Win-condition catalogue & tie-breaks. The exact set of win conditions and the tie-break rules (and how each is recorded so replay is deterministic).
  2. Start / holeshot & lap model. Gate-start vs staggered start, how the first lap is defined, and how splits/sectors derive — ties to the gate/split model in Timer Adapters.
  3. Frequency / channel allocation ownership. Whether the engine (it knows the heat) or the adapter (it knows the hardware) owns channel assignment and conflict avoidance — shared with the Timer Adapters open decision.
  4. Live / partial ranking semantics. How a generator exposes a meaningful current ordering mid-format (partial standings, provisional seeds).
  5. Manual-adjustment operation set. The full set of pre-fly RD operations (re-seed, move, swap, byes, withdrawals) and how each is modelled as an event.
  6. Per-format specs. The concrete rules of each named format (MultiGP P9–P16, FAI, double elimination, Chase-the-Ace, ZippyQ) — each its own spec, written as it's built, validated against this interface.
