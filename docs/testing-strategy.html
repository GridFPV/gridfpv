GridFPV

Testing Strategy

Internal design doc · how we keep race-timing logic correct without depending on a live external backend

How GridFPV earns trust in its results. The whole system is built so that correctness is a property we can replay, not one we have to witness live: pure translators with golden cases, recorded sessions replayed into a deterministic engine, and projection fixtures that fold marshaling in. The one rule everything else serves — no test depends on a live, shared, or production external backend (the Velocidrone game servers above all); recorded-session replay is the deterministic backbone. A self-hosted, disposable instance we fully control — dockerized RotorHazard — is fair game for live integration tests, because we spin it up and tear it down ourselves.

This doc owns the correctness strategy: the guardrail, the test levels, the fixture formats, and what each layer must prove. It defers the concrete win-condition and tie-break catalogue to Race Engine §7, the exact canonical-event and signal-context shapes to Timer Adapters, and the wire-contract shapes to Protocol — this doc tests against those interfaces, it doesn't define them. CI selection, build sequencing, and coverage gates belong to the Roadmap. When this doc and the Vision disagree, the Vision wins.

1. The hard guardrail

No test depends on a live, shared, or production external backend. No automated test — unit, integration, or end-to-end — may depend on a running Velocidrone game server, a shared/production RH deployment, or any source we don't fully control. Those backends are non-deterministic, shared, and out of our hands; a suite that leans on one flakes, can't run on a contributor's laptop, and can't run at all without the gear in the room. Correctness instead rests on recorded-session replay and golden cases: fixed inputs captured once, checked into the repo, and replayed deterministically forever — the hermetic backbone, and the only option for Velocidrone, which is fixtures-only. What this rule does not ban is a source we own and dispose of ourselves: a self-hosted, disposable instance — the dockerized RotorHazard we spin up and tear down — may back live integration tests, including in CI, because it is reproducible and entirely under our control. Recorded replay stays the backbone; controlled-live RH is an added integration level on top of it.

This is not a compromise we tolerate; it is the design working as intended. Because adapters are pure translators and the engine is a pure function of the log (Race Engine §6), every behavior we care about is a pure function of recorded bytes. There is nothing about a live timer that a faithfully recorded session doesn't capture — so recording it once and replaying it is strictly better than re-flying it, and it is repeatable.

Where the line actually falls: the ban is on depending on a live shared or production backend — the Velocidrone game servers above all, which stay fixtures-only. It is not a blanket ban on live sources in CI. Live integration tests against the dockerized RotorHazard are permitted, CI included, because that instance is disposable and ours to control (§5). Capturing fixtures from real sources, and a human sanity-checking the adapter against a live Velocidrone build before a release, remain deliberate off-CI activities that produce fixtures and confidence — never a gate the automated suite leans on a third party for.

2. Adapters — golden cases over pure translators

An adapter's entire job is: source input in, canonical events out, no race logic (Timer Adapters §1). That is exactly the signature of a pure function, so it is tested exactly that way — a golden case is a recorded source-input fixture paired with the canonical events it must produce.

Given (fixture)AdapterAssert (golden output)
A recorded Velocidrone WebSocket message streamVelocidroneThe exact ordered Pass / lifecycle / CompetitorSeen events, with split indices and source timestamps

A scripted sequence of manual UI entriesManualPasses with wall-clock timestamps, no signal/calibration

The fixture is the raw source bytes/frames as they actually arrived; the expectation is the canonical event list serialized via the same generated wire types the rest of the system uses (§7). A change to an adapter that alters its output is then a visible diff against the golden file — reviewed deliberately, not discovered in production. Because adapters emit observations, not derivations, these tests assert passes and lifecycle only — never laps, results, or standings, which are the engine's job.

A golden case pins a translation, not an interpretation. Adapter goldens prove "these source bytes mean exactly these canonical observations." They must stay free of any notion of a lap or a winner — if a lap concept leaks into an adapter test, race logic has leaked into the adapter, and the test has caught a design bug.

Two adapter properties get focused cases beyond happy-path translation: clocks (a fixture spanning a source-clock-to-session-timeline offset, asserting intervals are computed from source time — Timer Adapters §4) and reconnect/dedup (a fixture that replays a mid-session drop and reconnect, asserting no pass is double-counted or lost via the source's sequence numbers).

IRLFixtures carry signal context (RSSI, enter/exit windows); goldens cover signal-rich passes and the calibration events a hardware adapter emits.

SimFixtures are pass-only and exact; goldens prove the model degrades cleanly to a source with nothing underneath the crossing.

3. Recorded-session replay

The backbone, called out as "correctness by replay" in Architecture §3. We capture real sessions once, store them as fixtures, and replay them through the real pipeline — asserting the projections come out identical every time. This is what the append-only spine and engine determinism buy us: same events in, same heats/results/standings out (Race Engine §6).

A captured session is just an ordered log of canonical events (the same atoms the live system appends). Replaying it means feeding that log to the engine and projection layer and comparing the derived output to a stored expectation. Nothing live is involved; the timer's role ended the moment the fixture was recorded.

Two capture sources feed replay, and they are deliberately different in character:

Dockerized RotorHazard
A controllable hardware-shaped source. We script or hand-run a session against it and record the Socket.IO traffic the adapter would have seen — yielding signal-rich, real-world-shaped fixtures (per-node RSSI, enter/exit, calibration) without any physical gear (Timer Adapters §8).
Recorded Velocidrone WebSocket feed
A capture of an actual sim session's WebSocket messages — passes, splits, lap totals, holeshot/spread — taken once against a live build and replayed forever. This is how we exercise the sim path with no game running in CI.

Fixtures live at two layers, and both are valuable. A raw source-input fixture (recorded bytes/frames) replays through the adapter and the engine, exercising the whole path; a canonical-log fixture (already translated) replays through the engine alone, isolating engine/projection behavior from adapter translation. Adapter golden cases (§2) reuse the raw fixtures; pure engine and projection cases (§4) use canonical-log fixtures, often hand-authored rather than captured.

4. Projection golden cases

Everything analytical is a projection over the log (Architecture §3), so each derivation stage gets its own golden cases: a canonical-log fixture in, the expected projection out. The chain runs passes → laps → heat results → ranking/standings, and each link is tested both end-to-end (full replay, §3) and in isolation with small hand-authored logs that target one rule.

  • Passes → laps. A pass stream (holeshot + crossings, optionally with splits) folds into a lap list — the first pass is the start, each subsequent lap-gate crossing completes a lap (Race Engine §4).
  • Laps → heat result. A lap list plus a configured win condition (most laps in a window, first to N, best consecutive) yields a finishing order, with ties broken by the recorded rule.
  • Results → ranking / standings. Completed heat results fold into a qualifying ranking or event standings.

Marshaling is tested as folding, never as mutation. The decisive projection cases append adjudication events to a raw-observation log and assert the projection reflects the correction — because corrections are appended events, not edits (Architecture §3). A fixture for each: DetectionVoided drops a phantom lap; LapInserted recovers a missed one; LapAdjusted moves a boundary; PenaltyApplied / HeatVoided reshape the result. The raw observations stay byte-identical across these cases — only the appended adjudications differ — which is itself the assertion that nothing in the past was touched.

A "void the void" case (a correction that supersedes a prior correction) pins the last-writer-wins-per-target resolution from Architecture §3. And a recompute-equivalence case proves the incremental projection (maintained as events append) and a full recompute-from-scratch over the same log produce identical output — the property that makes crash recovery and retroactive metrics safe.

IRLMarshaling fixtures are heavy: signal-based lap recovery, re-timed enter/exit, phantom-lap voids from interference.

SimMarshaling fixtures are light: mostly heat-void and discard-and-re-run; the captured detection is already exact.

5. The dockerized RotorHazard's role

The dockerized RH instance plays two roles: a fixture factory and a permitted live integration-test source, CI included. Because we spin it up and tear it down ourselves, it is reproducible and disposable — so unlike a shared or production backend it can back automated tests directly. It lets us produce realistic hardware-shaped fixtures and run live integration checks of the real adapter against a real (if virtual) source.

UseIn CI?Why

The same applies to a live Velocidrone build: it is where the Velocidrone WebSocket message schema is captured and where a human confirms the adapter against the real feed (Timer Adapters §9). Once captured, the schema and a sample session become fixtures, and the live build never enters an automated run — Velocidrone stays fixtures-only. The bright line is the backend, not liveness: no shared or production external backend in tests (the Velocidrone game servers stay fixtures-only), while a self-hosted disposable instance we own — dockerized RH — may back live integration tests, CI included.

5.1 Emulated-signal races — driving RH's real pipeline

Beyond capturing fixtures and bare-lap injection, the dockerized RH can be driven by emulated node-output streams. RotorHazard's mock node interface reads a per-node mock_data_{N}.csv — the post-detection signal a real timer node sends the server (per-tick RSSI, peak/nadir, a crossing flag, and an incrementing lap id) — and runs it through its real lap-recording pipeline. So a generated signal stream produces a genuine RH race over Socket.IO, which our adapter translates exactly as it would a hardware event. This sits a layer above the two simpler modes:

LayerDriven byExercises
Recorded-session replaychecked-in canonical fixturesadapter translation + projection — fast, deterministic, no container
Bare-lap live (simulate_lap)injected passesthe live Socket.IO transport + lap recording; signal detection bypassed
Emulated-signal race (mock_data)generated RSSI / crossing streamsthe full chain — emulated signal → RH detection/recording → Socket.IO → adapter → projection, with signal context

A small generator turns a high-level scenario (per node: lap cadence, peak RSSI, active vs silent) into the CSVs; the harness mounts them into a disposable container, runs the race, and asserts the translated result. Because the mock reads its file continuously (decoupled from race start), exact lap timing is approximate — assertions are structural and tolerance-based (lap counts, per-node independence, signal magnitude, dedup over re-sent snapshots), not exact microseconds.

Why this matters going forward. This is the closest thing to a real race we can run in automation, and it generates a genuine timed lap stream on demand. As the Race Engine lands, the same harness becomes the way to test every timing-dependent stage end to end — the heat-loop state machine, scoring and win conditions, marshaling, and format advancement — driven by realistic, scriptable signals rather than hand-built fixtures. Edge cases (missed crossings, simultaneous passes, marginal signal, silent nodes) are expressed as signal scenarios.

The harness is a local class — it needs Docker, so it stays out of the shared pipeline; cargo xtask live spins each disposable RH up and down. See crates/adapters/tests/ (the generator + scenario tests) and docker/rotorhazard/.

6. Testing the format generators

Format / qualifying generators are a pure function of state too (Race Engine §3): given the seeded field, config, and the results of completed heats, a generator emits the next heat(s), declares completion, or exposes the current ranking. That makes them ideal for table-driven tests — a table of (seeded field + config + completed results) → expected (next heats / advancement / final ranking).

  • Advancement. Given a round's results and a "top-N advance" config, assert exactly who moves up, who is eliminated, and the seeds of the next heats.
  • Completion & final ranking. Given the last results, assert the generator declares the format complete and exposes the correct final ordering.
  • The dynamic case. ZippyQ / rolling is the honesty-forcing format (Race Engine §3) — a table that adds rounds on demand and asserts the generator produces sensible next heats from current state, never a precomputed schedule.
  • Recorded outcomes. Any randomness (a seeding draw, a coin-flip tie-break) is supplied as a recorded-outcome event in the fixture, so the table is deterministic and replay never re-rolls it (Race Engine §6).

These tests need no log replay and no timer at all — they exercise the generator contract directly. As each named per-format spec is written (MultiGP P9–P16, FAI, double elimination, Chase-the-Ace), it arrives with its own table of cases validated against this same interface.

7. Test levels

The levels mirror the Director's data path — translate in, derive, serve out — and each proves a different claim. Nothing above unit level touches a live source; replay is the seam.

Unit
Pure functions in isolation: adapter translators (golden cases, §2), the derivation stages (passes→laps→results→standings, §4), and the format generators (table-driven, §6). Fast, hermetic, the bulk of the suite.
Integration — replay
A recorded session (raw or canonical) replayed through the assembled adapter → log → engine → projection pipeline, asserting the derived projections (§3). Proves the pieces compose and that determinism holds end-to-end over the spine.
End-to-end — shadow against recorded events
Replay a full captured event's log against the running Director (store, projection maintenance, server) and assert the projections served over the protocol match the golden output — a "shadow" run of a real event with the live source removed. Exercises incremental maintenance, recompute-equivalence, and crash-recovery (reopen the log mid-replay, rebuild, continue) as the spine promises.
Protocol / contract
Because the wire types are generated from Rust into TypeScript (Architecture §6, Protocol), the generated types are a contract test: the build fails if Rust and TS drift. Beyond generation, fixtures of serialized snapshot/change-stream messages are decoded by a TS client to prove both ends agree on the shapes — and the same generated types serialize the canonical-event fixtures used everywhere above, so one definition keeps fixtures, engine, and clients in lockstep.

8. Open decisions

  1. Resolved — Fixture format & storage. Fixtures are stored as JSON and checked in alongside the code: per-adapter source/canonical fixtures under crates/adapters/src/*/fixtures/ and replay fixtures (events + golden lap lists) under crates/app/tests/fixtures/, versioned with the schema. Signal history stays a sidecar rather than inline (the sidecar format lands with the hardware-signal extension; today's fixtures carry the inline rssi_peak).
  2. Golden-update workflow. The mechanism for regenerating golden outputs when behavior changes intentionally (an "accept new goldens" command), and the review discipline that keeps an accidental change from being rubber-stamped. Accepted: an "accept goldens" command regenerates outputs, paired with a mandatory diff review so no change is rubber-stamped.
  3. Resolved — Capture tooling. A standalone recorder (docker/rotorhazard/capture_frames.py) drives the dockerized RH over Socket.IO and dumps its frames to JSON; that produced the checked-in ground-truth capture. The emulated-signal harness (§5.1) goes further — generated mock_data RSSI streams drive RH's real pipeline. A live Velocidrone build stays fixtures-only (no automated run).
  4. Property-based testing scope. Whether to add generative / property tests over the projection layer (e.g. "marshaling never loses a raw observation," "incremental == recompute for any log") on top of the enumerated golden cases. Accepted: add property-based tests over the projection layer on top of the enumerated golden cases.
  5. Determinism enforcement. How non-determinism is kept out of the engine in practice — banning wall-clock/RNG reads in the pure path, and asserting byte-identical projections across repeated replays as a CI check. Accepted: no wall-clock or RNG reads in the pure path, enforced by byte-identical replays as a CI check.
  6. Cross-version replay. Whether old fixtures must replay cleanly against a newer engine/projection (a regression guarantee for the open-data promise), and how that interacts with intentional scoring changes. Accepted: replay is byte-identical within a projection/contract version; an intentional change is a new recorded version, with the old fixtures deliberately re-blessed.
