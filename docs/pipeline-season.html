Phase 5 — Championship / Season

Pipeline deep dive · what this phase must do

Beyond a single event. Link events into a season and compute standings across all of them — the cross-event layer that turns individual races into a championship.

This is a deep dive on one phase of the event pipeline, kept lighter than the others: it is optional and cross-event, and it leans on the optional Cloud. The single-event pipeline stands on its own without any of this. Warehouse and Cloud details live in the Architecture doc (coming soon).

Role

optional · cross-event Per class. Aggregate results across many events into season standings.

A season links several independently-run events and computes standings across them, per class. Its output is the season/championship leaderboard and any qualification pathways. Nothing here is required to run a race — it sits on top of completed events.

Capabilities

Link events into a season

  • A season groups multiple events by reference. Events are created and run independently; they don't need to know about a season while they run — the season pulls their results afterward.

Scoring

  • Configurable, with presets — finishing-position points per event, best-N-of-M (drop your worst events), or cumulative total, with configurable tiebreakers.
  • Standings are computed per class, consistent with classes being self-contained competitions.

Standings & qualification

  • A season leaderboard per class, updated as member events complete.
  • Qualification pathways / cutoffs — a Global-Qualifier → championship analog — modeled lightly here (how much to build vs leave to the league is an open decision).

Where it's computed

  • The Director can compute a season across its own events fully offline — a self-hoster can run a local season with no internet.
  • The Cloud aggregates across all events and chapters and is authoritative for broader, cross-chapter / global standings. Consistent with the offline-first Director and the optional Cloud.

Open data

  • Season standings are exportable, available through the public API, and embeddable — ties to the open-data vision and the Cloud warehouse.

Sim vs IRL

BothScoring works identically — points are points. Sim leagues and IRL chapters aggregate the same way; whether a season is per-discipline or can mix sim and IRL is a configuration choice (see open decisions).

Entities & data implied

What this phase needs to exist (conceptual — not a schema; the Architecture doc formalizes it):

Season
name, member events, scope (per class), scoring config (scheme + tiebreakers), qualification rules.
Season standing (derived)
per pilot per class: aggregated points, events counted, rank.
Event result contribution
each event's per-pilot result, feeding the season aggregation.

Computed on the Director (its local events) and the Cloud (the authoritative aggregate); leans on the Cloud warehouse, where raw laps are retained and metrics are derived.

Open decisions

  1. Season scope. Strictly per class, or can a season span classes / mix sim and IRL?
  2. Director ↔ Cloud reconciliation. When both compute a season, how do the Director's local view and the authoritative Cloud aggregate merge?
  3. Qualification modeling. How much championship-qualification logic to build versus leave to the league.
  4. Participation points. Attendance / participation points and minimum-events thresholds.
  5. Cross-chapter identity. The same pilot across chapters (ties to the Setup identity decision).
