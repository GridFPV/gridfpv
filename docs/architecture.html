GridFPV

Architecture

Internal design doc · system shape, stack, and the one-protocol contract

The technical shape of GridFPV: the components, the chosen technology stack and why, the append-only spine that makes everything else derived, and the single read/realtime contract that the Director and the Cloud both speak.

This doc decides system shape and stack. It deliberately defers the things that earn their own docs: the adapter interface internals (Timer Adapters), the wire contract (Protocol), the Cloud warehouse and season model (Cloud & Season), the client surfaces (Clients), the broadcast subsystem (Streaming), external integrations (External Integrations), correctness strategy (Testing Strategy), and build sequencing (Roadmap). When this doc and the Vision disagree, the Vision wins.

1. System shape

GridFPV is one authoritative application — the Director — plus an optional Cloud and a set of web clients. The Director owns the truth for the duration of an event and runs end to end with zero internet. The Cloud is a relay and a long-term warehouse; it is never in the critical path of a live race.

The non-negotiable stances, restated as architecture:

The Director is authoritative and offline-first. It embeds its own server and store; a full event runs with no external dependency.

The Cloud is optional. A relay for off-LAN viewers and a warehouse for long-term stats. Its absence degrades nothing on race day.

One protocol, two transports. One read/realtime contract. The Director serves it on the LAN; the Cloud serves the identical contract off-LAN. Clients can't tell which they're talking to.

2. Technology stack & rationale

The stack is chosen to serve one hard requirement above all: a race director runs a single self-contained binary, no installed dependencies, on Windows, Linux, and macOS, and gets a friendly native window — not a "open your browser and type an IP" experience.

Why these

  • Tauri over Electron — Tauri uses the OS webview instead of bundling a browser, yielding the small single-executable-style binary the single-binary goal demands. Electron ships a large multi-file bundle and concedes that goal.
  • Rust core — physical timers (serial/USB) and a process that owns the truth offline for hours reward Rust's reliability and mature async + serial ecosystem. "It cannot crash mid-heat" is a feature when there is no cloud to fall back to.
  • One protocol becomes literal code reuse — the embedded server is a Rust crate; the Cloud reuses the same crate behind a storage trait (SQLite on the Director, Postgres in the Cloud). The contract is built once.
  • The RD console is just a co-located web client. The Tauri window loads the same web UI that talks to the same local API the racer PWA and overlays use. The native window costs nothing architecturally — it honors "one protocol" rather than bypassing it.

Considered and set aside: Go + Wails was the strong runner-up (excellent single-binary story, gentler curve) — Rust wins on hardware integration and race-day robustness. Electron is easiest for a JS-only team but loses the single-binary/no-deps goal. The frontend framework (React vs Svelte) is intentionally still open (see §11).

3. The append-only spine

Every event records raw timing as an append-only log. That log is the single source of truth. Everything analytical — standings, leaderboards, brackets, career stats — is a projection derived from it and can be recomputed at any time.

Append-only truth. Adapters and the race engine only ever append canonical events. Projections never feed back into the log.

What this design buys, concretely:

  • Retroactive metrics. A new statistic (consistency score, head-to-head record) is just a new projection over the existing history — no migration of "truth," only a recompute.
  • Resumable sync. The Cloud push is an offset into the log; a dropped connection resumes from the last acknowledged offset. No reconciliation, no conflict — the log is the order.
  • Trivial export & open data. The SQLite file is the whole event. Export, replay, and the public read API all read the same log.
  • Correctness by replay. A recorded session replays into the same projections deterministically — the backbone of the testing strategy.
  • Crash recovery for free. If the Director restarts mid-event, it reopens the log and rebuilds projections — the in-flight race resumes with nothing lost. What's on disk is always the truth.

Corrections & marshaling

Append-only does not mean the past can't be fixed — it means we never mutate or delete an entry. A wrong timing event is corrected by appending a correction that the projection layer folds in; the mistake and its correction both remain in the log, in order. This works because the log holds two kinds of entry with different semantics:

Raw observations (from adapters)
What a timer actually reported — "node 3 saw a gate pass at t=12.345." Genuinely immutable: the timer did report it, even if it was wrong. Adapters only ever append these.
Adjudications / marshaling (from the RD or rules)
Decisions layered on top that reference raw events by id — void a phantom lap, insert a recovered lap, adjust a lap boundary, apply a penalty, disqualify a pilot. Also appended, never destructive.

Current truth is the projection that folds raw observations and adjudications together. Typical marshaling actions are simply appended events — DetectionVoided, LapInserted, LapAdjusted, HeatVoided, PenaltyApplied. A marshal who corrects wrongly appends another event that supersedes the prior one (void the void); resolution is last-writer-wins per target, by log order, and nothing is ever lost.

Why this fits racing. Results are adversarial and disputes are routine. An append-only log makes every correction auditable (who, when, why), keeps Cloud sync a simple higher-offset append rather than a reconciliation problem, and lets standings recompute deterministically after any ruling.

IRLMarshaling is heavy — recover missed laps from signal history, re-time enter/exit points, correct phantom laps from interference.

SimLighter — mostly abort / restart and discard-and-re-run; the sim's own detection is clean.

4. Conceptual data model

At the conceptual level — not table schemas, which belong to the docs that own each area — the domain is three kinds of thing: the log (the only source of truth), the configuration that frames an event, and the projections derived by folding the log.

Event
The top-level container: name, date, the enabled phases (the configurable pipeline), and the classes it runs. Everything below belongs to an event.
Class / category
A field within an event (e.g. Mini, Micro, a sim class) with its own format and bracket — phases run per class.
Track
The layout flown — a physical track for IRL, or a Velocidrone spec track (with its track id) for sim.
Pilot & entry
A pilot is a person, ideally a stable identity across events (the global registry; see §9). An entry is a pilot's participation in one event's class — check-in / presence, plus the binding from a timer's local reference (a node seat, a sim player name) to the pilot.
Heat / round
Scheduling structures the race engine produces — who flies together, when, in which round. Generated by the format and adjustable before they fly.
Timing & race events (the log)
The append-only entries: raw observations from adapters, race-state events from the engine, and adjudications from marshaling (see §3). The only source of truth.
Projections
Everything derived — lap lists, heat results, the qualifying ranking / seed, bracket state, event standings, and (in the Cloud) career and season stats. Recomputable from the log at any time.

The dividing line: if it's an observation or a decision, it's a log entry; if it's an answer computed from those, it's a projection. Configuration is captured in the log too, so the whole event — setup through results — is reconstructible and exportable from one ordered history. Concrete schemas are deferred to the docs that own each area.

Storage tiers

Physically this lands in three tiers. Each event is its own append-only log — the SQLite file that "is the event," portable and replayable in isolation. The Director also keeps a small catalog store spanning events: the local pilot registry, app configuration, and the list of events it owns. The Cloud is the third tier — many events' logs aggregated into the warehouse. The per-event file stays the unit of truth and export; the catalog and warehouse are conveniences layered around it.

5. Components

Timer adapter layer
One interface in front of every timing source (Velocidrone first, then RotorHazard, LapRF, manual). Adapters are pure translators: source-specific input in, canonical timing events out. The interface internals are specified in Timer Adapters.
Race engine
The reusable heat loop (schedule → stage → arm → race → land → score → advance → next), advancement rules, and a pluggable registry of bracket / qualifying generators. It consumes canonical timing events and appends race-state events. Its design — the generator registry, advancement, and multi-class scheduling — is specified in Race Engine.
Append-only log + projection engine
The source of truth and the derivation layer. Projections are maintained incrementally as events append, and are fully recomputable from the log on demand.
Embedded server
The axum HTTP + WebSocket service that is the protocol: reads of projections, a realtime subscription to live changes, and authenticated write/control endpoints for the RD. Bound to the LAN so other clients can reach it.
Web clients
The RD console (in the Tauri window), the racer/spectator PWA, and OBS overlays — all the same kind of thing: a web client of the protocol. Only their transport and their permissions differ.
Cloud (optional)
Consumes the one-way log push, serves the identical protocol to off-LAN viewers, and aggregates many events' logs into the long-term warehouse.
External sync
MultiGP RaceSync (roster import, results push) and the open-data read API / exports — see External Integrations. Like the Cloud it needs internet and reads only derived projections, so it is never in the live critical path.

6. One protocol, two transports

There is exactly one read/realtime contract. A client opens it, fetches a snapshot of the projections it cares about, then subscribes to a realtime stream of changes over WebSocket. The same contract is served by the Director (on the LAN) and by the Cloud (off-LAN) — a client is configured only with a base URL.

Contract defined once, in Rust. The wire types live in a shared Rust crate — today the canonical event model (gridfpv-events), extended with the protocol's snapshot/read types as they land — and are generated into TypeScript for the frontend, so the Director, the Cloud, and every client share one definition that can't drift. (The event-log vocabulary already generates to TS via ts-rs with a CI drift check; the projection/snapshot types get their own bindings when the protocol crate arrives.)

As built (v0.4): the gridfpv-server crate owns the protocol wire types (snapshot/stream/control/error/version), generated to TS in bindings/ alongside the event model — one definition the Director, Cloud, and every client share. Wire types are generated from Rust with ts-rs across the crates that own contract types — gridfpv-events, gridfpv-projection, gridfpv-engine, and gridfpv-server (the protocol contract) — exported to repo-root bindings/. The protocol contract version is a single monotonic u32 (CONTRACT_VERSION), bumped only on a breaking wire change; additive changes an older client can ignore do not bump it.

Exact message shapes (snapshot format, the change-stream envelope, auth) are a protocol spec of their own. The architectural commitments here are: read + realtime-subscribe, transport-agnostic clients, and one type definition.

7. Clients & connectivity

The racer/spectator client is a PWA — the universal web client. Native is deferred but kept cheap: the same web client can later be wrapped in a Capacitor shell, exactly as the Director's UI is wrapped in Tauri. The web protocol-client is the constant on both ends; native shells are optional enhancements, not rewrites.

How visibility actually plays out depends on venue connectivity:

  1. Shared LAN, no internet — racers on the LAN reach the Director directly: live, low-latency, zero internet. The Cloud is dark.
  2. Director has internet (venue wifi, or even a phone hotspot) — the Director pushes the log to the Cloud, which relays the live event to anyone, anywhere. This is the primary broad-visibility path, not the LAN.
  3. No internet, no shared LAN — only the RD's screen plus whoever joins a local hotspot. The race still runs (the Director is authoritative offline); visibility is simply limited.

The LAN PWA is intentionally degraded. A plain-HTTP LAN address is not a browser "secure context," so service workers, install, and web push are unavailable there — but live viewing over WebSocket works fine. Installability and push notifications ride the Cloud transport (HTTPS, and APNs/FCM need internet regardless). So LAN gives in-page live alerts; true push is a Cloud-era feature. A future native client is the way to get LAN access and real push together — another reason native stays on the roadmap.

8. The Cloud

The Cloud is optional and never authoritative. It receives the Director's one-way, resumable log push and exposes two surfaces that share one component library:

Live race surface
The same one-protocol PWA the Director serves — realtime, single-event, latency-sensitive. Runs identically on either transport.
Long-term portal
Career profiles, season standings, open-data dashboards, embeddable widgets. Cloud-only by nature — the Director only knows one event; this reads the accumulated warehouse. Read-heavy and cacheable — the opposite scaling profile from the live surface.

Because the two surfaces scale oppositely, splitting them into separate virtual hosts (a dynamic realtime host vs a heavily-cached, possibly mostly-static stats host) is a reasonable deployment choice — left as an ops decision, not an architectural one. Season/championship aggregation lives here too and will be detailed alongside the Cloud warehouse design.

9. Security, trust & identity

The trust model follows from offline-first: the Director is authoritative on the LAN, and access splits into read and control.

Control is privileged; reads are open on the LAN. Running the race — race control, marshaling, configuration — requires the RD's authenticated role. Watching it (racer PWA, overlays) is open, or lightly tokened, to anyone on the LAN. Control authority never leaves the Director.

The Cloud authenticates accounts but is never authoritative. Off-LAN viewers reach the Cloud with accounts, but the Cloud only ever serves the read contract and relays — no race is controlled through it.

Identity has two layers. Within an event, a timer's local reference (a node seat, a sim player name) is bound to a pilot at registration. Across events, pilots ideally share a stable global identity (the registry) so career and season stats accrue to one person. Because the Director runs offline, it can operate with purely local pilots and reconcile them to global identity later, on sync — so identity never blocks a race.

Wire-level mechanics — how the RD role authenticates, token/session format, and how read access is scoped on LAN vs Cloud — are the Protocol spec's job. The cross-event registry and the reconcile-on-sync rules belong to Cloud & Season. This section fixes only the trust boundaries.

10. Streaming & broadcast

Integrated broadcast is a stated goal, and it splits into two halves — one we get for free from the protocol, and one that is a genuine Director subsystem.

Overlays are just protocol clients. Staging, leaderboard, split-screen, podium, and bracket overlays are web pages driven by the same read/realtime contract as every other client, loaded as OBS browser sources. They need nothing special — live race state already flows to them.

Broadcast control is an optional Director subsystem. Driving OBS (scene switching via its websocket API, tied to live race state) and handling video capture / RTMP-style inputs is active output the Director performs — distinct from serving overlays. It consumes projections and reacts to race events, but never sits in the timing critical path.

The subsystem's design — the OBS control model, capture / RTMP handling, and the overlay catalogue — is deferred to the Streaming doc. The architectural commitment here: overlays are protocol clients, and broadcast control is an optional consumer of live state, never a dependency of timing.

11. Deferred decisions & where they're tracked

What this doc deliberately doesn't settle, recorded so nothing is silently assumed.

Recorded defaults (revisitable)

  • Projection maintenance — incremental as events append, with full recompute from the log always available.
  • Realtime delivery — WebSocket (snapshot + change stream) is the working default; SSE is the fallback to weigh in the Protocol spec.

Open — tracked in their own docs

  1. Resolved — Frontend framework: Svelte. Not load-bearing (every framework consumes the same generated types); chosen for leanness and realtime/overlay fit — rationale in Clients (React recorded as the revisitable alternative).
  2. In progress — Adapter internals & how "raw" the raw timing is. The canonical event model is built (gridfpv-events), and the first two adapters (RotorHazard, Velocidrone) translate validated real wire formats; a lap is a re-derivable projection of the pass stream. Remaining detail (richer signal summary, signal-based recovery) — Timer Adapters.
  3. Protocol message shapes, realtime transport & auth. Snapshot format, change envelope, WS-vs-SSE, and the RD's privileged write path — Protocol.
  4. Cloud warehouse, season model & identity reconciliation. The aggregate store, season scoring, and merging local pilots into the global registry — Cloud & Season.
  5. Streaming & broadcast subsystem. OBS control, capture / RTMP handling, and the overlay catalogue — Streaming.
  6. Time & clock authority. The authoritative clock (monotonic for race timing vs wall-clock for logging) and how adapter timestamps — sim time vs hardware time — map onto one timeline — Timer Adapters.
  7. Log & schema versioning. How the event-log format evolves while keeping old events readable for long-term open data — paired with the Protocol contract versioning.
  8. Race engine design. The pluggable generator registry, advancement, and multi-class scheduling — Race Engine.
