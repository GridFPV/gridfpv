GridFPV

RotorHazard Plugin

Internal design doc · the required in-process RH integration + its sliced build plan

The decided primary RotorHazard integration (D16): a small GridFPV plugin that runs inside the RH server with RHAPI access, replacing the socket-API ceiling. It makes the socket workarounds native — live dense RSSI (no save-then-pull), clean start/stop bypassing RH's RMS staging, per-node passes without the seating dance, and threshold access that unblocks the draggable-threshold recalculate marshaling feature (#3). It reuses RH's entire proven stack — node firmware, RMS, and the detection moat — at a fraction of the dropped own-the-stack cost.

This doc owns the plugin architecture, the Grid↔plugin protocol, the required-with-guided-install onboarding, and the sliced build plan. It is downstream of Timer Adapters (the canonical event model — unchanged; the plugin is a richer RH adapter behind the same vocabulary) and D16 (the direction). Where this doc and Timer Adapters disagree on the event model, Timer Adapters wins.

1. Principles

Grid owns timing; the plugin is start/stop/get-data. The plugin never decides when a race begins or ends — Grid does, on Grid's clock. The plugin exposes a thin executor surface (seat, start, stop, read signal, set threshold) and reports observations. This is the same adapter philosophy as the socket path; only the transport and fidelity change.

Same canonical events, richer source. The plugin still produces Pass, CompetitorSeen, and SessionStarted/Ended — the canonical model is untouched. What changes is that signal context arrives live and dense instead of via a post-race pull, and the control surface is native instead of worked-around. The Grid-side RH adapter gains a new transport (the plugin channel), not a new event model.

Required means guided, not gated. Grid detects a missing or incompatible plugin and offers a one-step install — it does not hard-fail with a cryptic error. Every serious RMS (FPVTrackside, LiveTime) already requires its own timing plugin, so this is the normal shape, not friction (D16).

Raw handles on the wire; friendly names resolved in Grid. The protocol carries raw handles — node-seat index, RH pilot id, frequency in MHz. Grid resolves callsigns and channel labels through the shared resolvers (CLAUDE.md). The plugin never invents a display name.

2. What the plugin taps (verified RHAPI surface)

The floor is RHAPI v1.3 (RotorHazard v4.3.0+); current is v1.4 (RH v4.4.0). The in-process mechanics were spiked against the harness image (cruwaller/rotorhazard:latest = RH 4.0.0-beta.4) and the API surface verified against the v4.3.0 and v4.4.0 source. A plugin is a directory under RH's plugins/ (where that is) with an __init__.py exposing initialize(rhapi) and a manifest.json declaring required_rhapi_version (gated by the loader at 1.3+); RH imports it and hands over the rhapi object. From there:

Event hooks — rhapi.events.on(evt, handler)
The race lifecycle and pass stream arrive as events, not snapshot diffs: RACE_STAGE, RACE_START, RACE_FINISH, RACE_STOP, RACE_LAP_RECORDED (the pass atom), CROSSING_ENTER/CROSSING_EXIT, ENTER_AT_LEVEL_SET/EXIT_AT_LEVEL_SET, FREQUENCY_SET, HEAT_SET.
Live dense signal — rhapi.interface.seats
The node list. Each Node carries current_rssi, node_peak_rssi, pass_peak_rssi, the nadir variants, enter_at_level, exit_at_level, frequency, index, and the dense per-pass trace history_values[] / history_times[] — read live, in-process. This is the save-then-pull killer.
Race state — rhapi.race
status, slots, pilots, laps, start_time_internal — read for attribution and to anchor the clock.
Clean control — rhapi.race.stage(args) / rhapi.race.stop(doSave)
Real, sanctioned methods at 1.3+ (in RHAPI 1.0 they were pass stubs monkeypatched at runtime — the floor avoids that). This is the clean start/stop, no socket stage_race / alter_race_format dance.
Calibration write — not RHAPI at all: set_enter_at_level / set_exit_at_level on the socket
There is no supported RHAPI calibration path on 1.3 or 1.4 — rhapi.interface is read-only in both (1.4 adds only add()). The working write is RotorHazard's own stock socket.io handler, on the connection the Grid adapter already holds — so calibration needs no plugin at all, which is what lets the Tune page (#355) work on a bone-stock RH. See the correction below for the shape and the two traps. For #3 recalc we mostly need the dense trace (below), not a live setter — see §3.
Seating — rhapi.db + rhapi.race.slots
Read/assign node-seat ↔ pilot in-process, no add_pilot/alter_heat socket round-trips and no new-pilot-id polling.
The channel back to Grid — rhapi.ui.socket_listen / socket_broadcast
At the 1.3 floor the plugin registers custom socket.io handlers (socket_listen(message, handler)) and pushes (socket_broadcast / socket_send) under a gridfpv_* event namespace — on RH's existing socket.io server. The Grid adapter already holds a socket.io connection to RH, so the plugin channel rides that same connection and port — no hosted blueprint, no second transport.

⚠ Correction (2026-08-25, #355): the frequencyset_alter calibrate route this document used to specify cannot work. It maps to RHData.alter_profile, which writes profile.enter_ats / exit_ats to the database, commits, and fires Evt.PROFILE_ALTER — and never calls interface.set_enter_at_level. The value persists and the timing hardware keeps detecting at the old threshold: a calibration that silently does nothing. It was never built; every mention of it below has been corrected.

What actually works, verified against RotorHazard v4.3.0 (the D16 floor, and what the field timers run) and v4.4.0 source — server.py::on_set_enter_at_level / on_set_exit_at_level and calibration.py:

  • Events: set_enter_at_level and set_exit_at_level.
  • Payload: { node, enter_at_level } and { node, exit_at_level }, where node is the 0-based seat index.
  • Identical on v4.3.0 and v4.4.0 — same event names, same payload keys. v4.4.0 differs only by an int(… or 0) coercion around the value, so one code path covers both and no version branch is needed.
  • No socket-level auth. The @requires_auth decorators in server.py guard Flask HTTP routes; zero socket handlers carry them.
  • It reaches the hardware. calibration.py writes the profile row, calls interface.set_enter_at_level, and fires Evt.ENTER_AT_LEVEL_SET — all three, which is exactly what frequencyset_alter does not do.
  • No echo. Neither handler emits anything in reply, so a write cannot be confirmed synchronously. The readback is load_data with {"load_types": ["enter_and_exit_at_levels"]}, which answers with an enter_and_exit_at_levels emit. Grid fires it after every write and the Tune page confirms by seeing the level come back — never by trusting the write's own response.

Two traps that cost a field day if they are rediscovered the hard way:

  • 0 is falsy. calibration.py tests the incoming level for truthiness (if not enter_at_level:), so a 0 means “ignore me and re-read the level off the node” rather than “set it to zero”. The old threshold survives while the write looks perfectly accepted. Clamp the minimum to 1.
  • 255 writes the profile but never reaches the detector. Node.is_valid_rssi is value > 0 and value < max_rssi_value — strictly less — and max_rssi_value is 255 at node API level ≥ 18. So RHInterface.set_enter_at_level drops it, while calibration.py has already written the profile row. And because RHUI.emit_enter_and_exit_at_levels serialises that profile row, not the node, the readback cheerfully confirms a level the detector never received. The readback proves “RotorHazard took it”, one step short of “the detector holds it”; staying inside 1..=254 is what closes the gap.

Capture — letting the timer measure the level (#355). The write above needs the RD to already know a number. An RD with a badly-tuned timer and no saved profile (#411) does not, and Grid deliberately ships no fabricated default — the right level depends on craft, VTX power, antenna and gate geometry, and a default would also change the hardware on first connect, the surprise D27's drift rule exists to prevent. Capture is the only non-guessing bootstrap: it measures the RD's own craft on their own gate.

Also stock RotorHazard, also no plugin, and verified byte-identical on v4.3.0 and v4.4.0 across server.py, calibration.py and interface/BaseHardwareInterface.py:

  • Events: cap_enter_at_btn and cap_exit_at_btn (server.py::on_cap_enter_at_btn / on_cap_exit_at_btn).
  • Payload: { node_index }, the 0-based seat index. Note the key. It is node_index here and node on set_enter_at_level — same socket, same node, two names. A wrong key raises a KeyError that @catchLogExcWithDBWrapper swallows into the log, so the emit “succeeds” and nothing is captured.
  • No auth, like every other socket handler in that file.
  • No preconditions. It needs no race, no crossing and no seated pilot — it works on a wholly idle timer, which is the entire point.

What it actually does — which is not what the name suggests:

  • The window opens at the emit, not at the pass. start_capture_enter_at_level arms a sampling window of CAP_ENTER_EXIT_AT_MILLIS = 3000 ms starting now. RotorHazard does not look back at a lap already flown. Any UI wording along the lines of “fly a lap, then capture” sends the RD to the gate three seconds too late — the control has to say that the timer starts watching the moment it is pressed.
  • It averages; it does not take the peak. Over the window the RSSI loop accumulates current_rssi and a sample count, and at the deadline the level becomes round(total / count). For the enter threshold only there is then one correction: if node_peak_rssi - level < ENTER_AT_PEAK_MARGIN (5), the level is pulled down to node_peak_rssi - 5. The exit branch has no such margin.
  • It is refused in complete silence. start_capture_*_at_level returns False — emitting nothing — when a capture of that threshold is already running on that node, or when the node's api_valid_flag is clear (nothing answering at that seat). An out-of-range node_index is an IndexError the exception wrapper logs and drops. This is the same hazard as the three writes RotorHazard silently ignored (#423), so Grid refuses a second capture of an in-flight threshold itself rather than dispatching one that will vanish, and treats “no new level came back” as a failure rather than a success.
  • This one does echo. Unlike the direct level set: when the window closes, new_enter_or_exit_at_callback calls calibration.set_enter_at_level (profile row, hardware push, Evt.ENTER_AT_LEVEL_SET) and rhui.emit_enter_at_level(node), broadcasting node_enter_at_level { node_index, level } roughly 3.0–3.1 s after the emit. Grid folds that into the tune tap, and also fires the ordinary enter_and_exit_at_levels readback once the window has elapsed — a gate's calibration is not a thing to stake on one unsolicited broadcast.
  • Confirmation is still by poll. Either way the level reaches the console as NodeSignal.enter_at / exit_at on GET /timers/{id}/signal, exactly as a typed level does. Grid records a captured level on Timer.calibration only once it has actually observed it (D27): recording one it never saw arrive would be the fabricated success this whole path exists to remove.

3. The Grid↔plugin protocol

A versioned gridfpv_* event namespace the plugin registers on RH's existing socket.io server (the same host/port RH already serves, default :5000, and the same connection the Grid adapter already holds). JSON encoding, versioned in the gridfpv_hello handshake. As shipped, request/response uses paired events, not socket.io acks (the hello is answered by a separate gridfpv_hello_ack broadcast); the ack model below is the original sketch — don't build against acks. Shipped channels: gridfpv_hello/gridfpv_hello_ack, gridfpv_signal, gridfpv_pass; everything else in the lists is unbuilt design (S3+). The two directions:

Control · Grid → plugin (gridfpv_* with ack)
gridfpv_hello (handshake: plugin version, RHAPI version, declared capabilities, node count) · gridfpv_clock_sync (NTP-style exchange — RH's monotonic clock demands it) · gridfpv_seat (assign node → {raw RH pilot id, callsign, frequency/channel}) · gridfpv_start / gridfpv_stop (Grid's go/finish — maps to race.stage() / race.stop()). There is no gridfpv_calibrate: calibration does not go through the plugin at all — Grid writes set_enter_at_level / set_exit_at_level on the stock socket it already holds (see the correction above), which is what lets the Tune page work on a plugin-less RH.
Data · plugin → Grid (gridfpv_* broadcast)
gridfpv_session (stage/start/finish/stop edges) · gridfpv_competitor_seen (a node seat went active) · gridfpv_pass (the atom: node seat, source timestamp, lap#/sequence, peak RSSI) · gridfpv_signal (live dense RSSI per node — current_rssi heartbeat plus the per-pass history_values window) · gridfpv_status (liveness + node/threshold snapshot).

The #3 recalc is a re-detection, not a hardware command. RH exposes no "re-run detection at new thresholds" call, so the draggable-threshold recalculate is a computation over the stored dense trace (the history_values Grid captured in S2): replay RH's enter/exit hysteresis at the marshal's chosen levels and propose the resulting laps. It needs the trace + a faithful copy of the detection rule — not a live setter. Pushing a marshal-chosen level forward onto the timer is the ordinary calibration write (set_enter_at_level, above), not a plugin route.

Each message maps 1:1 onto a canonical event: pass → Pass (with signal context attached), competitor-seen → CompetitorSeen, session → SessionStarted/Ended. The Grid-side adapter (crates/adapters/src/rotorhazard) keeps its translator and gains a plugin transport alongside the socket one — the same dedup-on-sequence and reconnect-resume guarantees apply (Timer Adapters §4–5).

4b. The socket-emit audit (#423)

Grid drives RotorHazard by emitting internal socket handler names — reverse engineered, not a supported API. Three of those writes shipped doing nothing, each returning success and each found by hand on the race director's bench after shipping: set_min_lap_time wrote an option RotorHazard does not have; frequencyset_alter wrote the threshold to the database and never pushed it to the detector; set_frequency's label sent "R8" where RH does int(data['channel']), aborting the whole handler on a ValueError. A fire-and-forget emit has no failure signal, so a dead write that reports success is the failure mode this audit exists to find.

Every row below was checked by reading RotorHazard's own source on both supported versions — v4.3.0 from the running container (the RHAPI 1.3 floor, and what the field timer runs) and the v4.4.0 tag — never inferred from a handler's name. A name is evidence of nothing: MIN_LAP_TIME named an option RotorHazard has never had, and unlimited_time is stored in a column called race_mode.

One correction the audit owes the record. “unlimited_time means the opposite of what it says” has been repeated in three issues, and against these two versions it is not true. On 4.3.0 and 4.4.0 alike, RHRace reads unlimited_time == 0 as “count down” and == 1 as “no time limit” — the attribute is honest, and Grid's unlimited_time: 1 lands correctly. What is confusing is one layer down: the ORM maps it onto a DB column still named race_mode (DB.Column('race_mode', …)), with a deprecated race_mode property kept beside it that logs a warning. So the hazard is real but it is a column name, not the field Grid writes. Restating the stronger claim would have been the same mistake this audit exists to stop.

The headline: RHAPI 1.3 and 1.4 are the same API for every one of these. The whole 1.3→1.4 diff is four additions — ui.register_function_binding, interface.add, server.set_min_mocks, server.set_restart_required — and not one of them touches an emit in this table. “Verify against 1.3 and 1.4” therefore collapses to a single answer everywhere, and “newer” was never a reason to move.

Legend. Lands? = does the emit actually reach a handler and take effect. Readback = how Grid confirms it, since none of RotorHazard's write handlers returns a value and several deliberately exclude the writing socket from their echo (noself=True). RHAPI verdict = would routing this through the plugin be genuinely better, not merely newer.

The original enumeration listed 17 emits; there are 25. Missing from it were alter_pilot, alter_heat, alter_race_format, set_enter_at_level, set_exit_at_level, cap_enter_at_btn, cap_exit_at_btn and gridfpv_hello — and alter_heat, the one that turned out to carry the unconfirmed write below, was among them.

The fourth dead write: current_race_marshal does not exist on v4.3.0. Not “behaves differently” — absent. Grid's own code called the two dense routes “newer RH” and “older RH” without ever naming which, and drove both, so the gap never showed in behaviour. It was invisible because it was driven, not because the emit worked. Both routes stay; the version each one serves is now stated where it is emitted, and request_marshal_data() — which previously sent only the 4.4.0 event and was therefore a silent no-op against the floor — now drives both.

The fifth, and the expensive one: the seating chain was never confirmed. seat_heat emitted add_pilot → alter_pilot → alter_heat per seat and then selected the heat as current — with no readback on the assignment at all. It could not have had one by accident: alter_heat answers noself=True, so its echo is delivered to every socket except the one that wrote, and @catchLogExcWithDBWrapper turns a handler exception into a log line. If a seat did not take, RH then held a current heat with an empty node — and its pass gate (pilot_id is not None and pilot_id != PILOT_ID_NONE) dismisses every crossing on that node, losing that pilot's entire run, while Grid reported a seated heat. That is the exact shape of the three writes that already cost bench time, with the largest blast radius of any of them.

And it is reachable, not theoretical. RHData.alter_heat resolves the slot as HeatNode.query.get(slot_id) — a bare primary-key lookup, not scoped to the heat — and then assigns slot.pilot_id unconditionally. A slot id that no longer exists gives an AttributeError on None, straight into the swallow. Worse, a slot id belonging to a different heat seats the pilot happily — on the wrong heat — while the heat Grid then makes current stays empty. Grid can produce exactly that: the slot ids come from “the freshest heat in whatever heat_data arrives”, and RotorHazard dispatches every socket event on its own greenlet, so a pre-add_heat snapshot is a legal thing to receive.

Fixed: after seating, Grid re-reads load_data{heat_data} and checks each slot's pilot_id on the heat it is about to race — which closes the wrong-heat case as well as the failed-write one. Every intended seat must be confirmed; anything less falls back to practice mode (no current heat), which still records every lap through RH's current_heat is HEAT_ID_NONE branch and costs only the dense RSSI trace — and says so, naming the callsigns that did not seat. The check re-asks until it confirms or times out, for the same greenlet reason: a single ask could read the pre-write snapshot and condemn a perfectly good heat.

⚠️ The readback itself needed care, because RHUtils.PILOT_ID_NONE is 0 on v4.3.0 and None on v4.4.0. Checking for one sentinel would have made every 4.4.0 slot read as seated — a confirmation step that confirms nothing, which is worse than the blind write it replaced. Both collapse to “empty” in one place, and a test pins both.

Noted, not fixed: the same sentinel split shows up on the way in. HEAT_ID_NONE moved 0 → None alongside PILOT_ID_NONE, so a practice-mode race (no current heat) reports race_heat_id: 0 from a v4.3.0 timer and null from a v4.4.0 one. Grid's session_id turns those into heat-0 and race — two names for one state, the first naming a heat that does not exist. It is left alone on purpose: it is consistent within a connection (a timer does not change version mid-event), it is an inbound decode rather than an emit, and SessionId is keyed on outside the adapter crate, so normalising it is a wider change than this audit's remit. Recorded where the code is, with the fix named, so the next person meets it as a decision rather than a surprise.

5. Onboarding — required, with a guided install

On connecting its socket.io link to a configured RH timer, Grid emits gridfpv_hello and awaits the ack (with a short timeout). Three outcomes:

Present & compatible
The ack returns the plugin version, RHAPI version, and capabilities. Grid prefers the plugin transport and surfaces a healthy TimerStatus. (The friendly timer name is shown, never the URL — CLAUDE.md.)
Missing
The handshake times out (no gridfpv_* handler registered). Grid shows a guided install: the plugin is a small folder dropped into RH's plugins/ directory followed by an RH restart. Grid offers the versioned plugin bundle to download plus the unzip-copy-and-restart steps (as shipped: download gridfpv-plugin.zip from the Director, unzip it, copy the inner gridfpv/ folder, restart RH — the same-host copy automation is a possible future nicety, not built). This is a prompt, not a hard error. (An RH older than v4.3.0 fails the same way and is told to update RH first.)
Present but incompatible
The handshake protocol_version differs from the Director's (compatibility is exact-equality today, widening to a band only if the protocol ever needs it). Grid offers the matching plugin version and explains the mismatch in plain language.

Where RH's plugins/ directory actually is. The guided install's last step is the one that stops people (field session, 2026-08-24). User plugins live at DATA_DIR/plugins — not PROGRAM_DIR/bundled_plugins, which is RH's own bundled set. DATA_DIR resolves through a six-step cascade (--data argument → datapath.ini in PROGRAM_DIR → an already existing ~/rh-data → PROGRAM_DIR if config.json sits there → the CWD if config.json sits there → ~/rh-data, created), so no single hardcoded path is right for everyone:

  • Modern default install — ~/rh-data/plugins/ (on a Pi, /home/pi/rh-data/plugins/). The usual answer, but a typical default, not a guarantee.
  • Legacy in-place install — <RotorHazard>/src/server/plugins/. RH v4.x actively prompts users to migrate off this, so both layouts are in the wild.
  • Vendor / custom rigs (e.g. a NuclearHazard timer, confirmed in the field) sit somewhere else again. Whatever the layout, it is the plugins/ folder beside RH's config.json / database.db, and RH logs Data path: <DATA_DIR> at startup.

And it frequently does not exist. RH only scans DATA_DIR/plugins if present (logging "No user plugins directory found." otherwise), so on a fresh install there is no folder to hunt for — it has to be created. This was the actual sticking point in the field.

The final layout is <DATA_DIR>/plugins/gridfpv/ holding __init__.py + manifest.json directly — no wrapper folder (the bundle is a zip, so it must be unzipped first). Rather than restate RH's own rules, the console links RotorHazard doc/Plugins.md.

Guidance only — no auto-detection. Reporting RH's real data_dir through gridfpv_hello_ack (RHAPI exposes it) was considered and dropped: the value is reachable only once the plugin is loaded, so it cannot help the first install — exactly the moment the RD is lost. It would add protocol surface for people who no longer have the problem.

Transition: while the plugin rolls out, the existing socket transport stays as a fallback behind the same adapter — a stock RH without the plugin still works at reduced fidelity (no live dense signal, no recalc), and Grid nudges toward the install. Once the plugin is the assumed path, the socket-workaround code (the save-then-pull, the alter_race_format hack, the seating dance) is deleted (S3's remaining work — as of v0.4.0-alpha.1 those are still the production control path; the save-then-pull is already suppressed whenever live signal is active).

6. Version & compatibility

Floor on RHAPI 1.3 (RH v4.3.0+); use the new features. The plugin requires RH v4.3.0+ (RHAPI 1.3, verified to carry socket_listen/ socket_broadcast, real race.stage()/stop(), and manifest.json + required_rhapi_version gating — not calibration, which has no RHAPI path at any version and rides RH's stock socket instead; see the correction). Current RH is v4.4.0 (RHAPI 1.4). The manifest.json declares required_rhapi_version 1.3 so RH's own loader refuses to load us into a too-old server, and Grid surfaces "update RH to v4.3.0+" as part of the guided install. We are comfortable making users update RH — every serious RMS requires a current timer (D16).

Harness reality (built, S0): cruwaller/rotorhazard:latest is stale at 4.0.0-beta.4 (only :latest is published) — below our floor. So the harness is not a tag swap: docker/rotorhazard/ builds a mock-node image from the RotorHazard v4.4.0 source (MOCK_NODE_SIGNAL=1 required). The MockInterface reads RSSI/history from a mock_data CSV, and the emulated-signal slice (S2) was validated against it.

7. Build plan — five slices

Each slice is a vertical cut, shippable before the next, and gated on cargo xtask ci + the full frontend gate (backend binding changes run the frontend gates too). The Grid↔plugin protocol is additive to the existing adapter, so each slice leaves the socket fallback intact until S3 deletes it.

Slice 0 — Current-RH plugin dev harness ✅ SHIPPED
Build a docker/rotorhazard/ image from RH v4.4.0 with MockInterface + an emulated-signal CSV, and extend cargo xtask live / rh-mock to mount the GridFPV plugin into the container's plugins/ dir. Unblocks testing every later slice against current RH. Built — plus the gridfpv_mock test plugin and the race-day autopilot harness on top.
Slice 1 — Plugin skeleton + handshake + guided-install UX ✅ SHIPPED
plugins/gridfpv/__init__.py (+ manifest.json, required_rhapi_version 1.3) registering gridfpv_hello via socket_listen (version/capabilities). Grid-side: the handshake probe, the required-with-guided-install flow (§5), and the adapter learning to prefer the plugin transport (socket fallback retained). Ships: Grid recognizes a plugin-equipped RH and walks a missing one through install. As built: the bundle is embedded in the Director at compile time and served at GET /plugin/gridfpv.zip (always matches the running Director); the handshake replies via a separate gridfpv_hello_ack event (not a socket.io ack) carrying protocol_version (checked for exact equality) and prestage_secs_was.
Slice 2 — Live dense RSSI → replace the save-then-pull ✅ SHIPPED
Plugin broadcasts per-node signal over the gridfpv_signal channel (current_rssi heartbeat + per-pass history_values window); Grid consumes it as the pass's signal context and the heat's trace. Retires the path-2 save_laps→load_data→get_pilotrace pull. Validated against the emulated-signal harness. Headline marshaling-fidelity win. As built, richer than sketched: gridfpv_signal is incremental (per-node base index, append-vs-replace, a final full flush on race stop, a 20k-sample window cap, 2 Hz decimation) — which resolves risk #5 (volume). The save-then-pull is suppressed while live signal is active and retained as the stock-RH fallback.
Slice 3 — Clean start/stop + per-node passes ◐ PARTIAL
Plugin executes seat (via rhapi.db), start (race.stage()), stop (race.stop()), and emits passes from RACE_LAP_RECORDED attributed by node seat. Grid still owns the timing. Status: live_pass (native RACE_LAP_RECORDED passes, deduped against current_laps) shipped; the prestage zeroing shipped (zero_prestage_pad). Clean start/stop has not — the Stage-time socket prepare/seat flow (staging-zero, seating dance) is still the production control path, recently hardened rather than deleted (effective-format re-prepare, 5 s stage retry, per-arming pass gating). Deleting those workarounds is this slice's remaining work.

#423 narrows what is left, and it is not what the slice's name says. The start/stop half has no case: on_stage_race and on_stop_race are race.stage() and race.stop(), byte-for-byte the calls RHAPI would make, identical on 4.3.0 and 4.4.0 — so routing them Director→plugin→RHAPI adds a hop and a capability gate to arrive at the same line of Python. Building it would be “newer” standing in for “better”.

The seating half does have a case, and a specific one: db.heat_add() and db.pilot_add() return the row they created. The socket dance cannot — it emits, waits up to 3 s for a broadcast, and infers the new id as “the highest” / “the one above the floor”, a heuristic that is wrong the moment anything else touches RH's heats or pilots concurrently. That is the piece worth building, it needs a socket fallback for the v0.3.0 field plugin, and until then the readback added in #423 is what keeps the dance honest.

Slice 4 — Draggable-threshold recalculate ◐ DELIVERED GRID-SIDE
A recalculate that replays detection over the stored dense trace at marshal-chosen enter/exit levels and proposes lap changes (Grid/marshal commits; RH truth is not mutated under the RD), plus an optional write-back of the chosen levels onto the timer. The marshaling graph gets draggable thresholds over the captured trace. The payoff feature owning-the-stack was for. Shipped ahead of the plugin slice, Grid-side: re-detection re-runs the enter/exit hysteresis over the captured trace in the console (preview-only; committed via the ordinary marshaling rulings) — resolving open decision #3 in favour of a faithful Grid-side reimplementation. The forward write-back landed in #355 — but as set_enter_at_level on the stock socket, with no plugin route and no gridfpv_calibrate (see the correction); pushing a marshaling panel's levels through it is the remaining follow-up.

8. Risks & open decisions

  1. Resolved — RH-only, no cross-RMS abstraction. RotorHazard is the only FPV timing system with a user-installable plugin API (FPVTrackside is compile-in C#; LiveTime and LapRF are fixed protocols; MultiGP is a cloud REST API whose RH integration is itself an RH plugin). Any future non-RH timer is a protocol adapter, not a plugin host, and the canonical event model already provides that seam — so we build concretely for RH and do not design a speculative cross-RMS plugin protocol.
  2. Answered — pass attribution across the pilot gate. RH's pass gate rejects crossings on unseated nodes ("Pilot not defined") and RACE_LAP_RECORDED only fires for laps RH records — so seating remains required even with live_pass. The Stage-time socket seating stays until S3 replaces it with in-plugin rhapi.db seating.
  3. Resolved — recalc detection fidelity. Decided in favour of a faithful Grid-side reimplementation of RH's enter/exit hysteresis, shipped in the console's re-detection (redetect.ts) over the captured trace — preview-only, committed through the ordinary marshaling rulings. In-plugin recalc is off the table.
  4. Satisfied — recalc is deterministic and non-destructive. The shipped re-detection proposes (never silently rewrites) laps, commits via void/insert rulings, and shares the marshal's removal record so a removed crossing is never re-proposed (Marshaling, D25).
  5. Resolved — live-signal volume. Shipped bounded: incremental per-node base-indexed appends, a 20k-sample window cap, 2 Hz decimation, and a full flush only at race stop.
  6. Install automation vs. instructions — same-host Grid can copy the plugin folder directly; remote RH gets download + copy-and-restart steps. Pick the same-host automation as the happy path.
