Cloud & Season

Internal design doc · the optional relay, warehouse, and cross-event layer · draft

The optional Cloud: an off-LAN relay for live events, a long-term warehouse for the accumulated history, and the cross-event season / championship layer. Never authoritative, never in the live critical path.

Early draft. This page captures scope and the open decisions routed here from the Architecture doc (see §8 and §9) and the Event Pipeline (Phase 5), so they're tracked in the right place. The design itself is not yet specified. When this doc and the Vision disagree, the Vision wins.

Scope

This doc will own:

  • The one-way resumable push — how a Director streams its append-only log to the Cloud, and resumes after a drop.
  • The warehouse — how many events' logs aggregate in Postgres, and what is stored raw vs projected.
  • The two surfaces — the live relay (the same one-protocol PWA) and the long-term portal (career, seasons, open-data, embeddable widgets), which scale oppositely (see Architecture §8).
  • The season / championship model — linking events, configurable scoring, season standings, and qualification pathways (Event Pipeline, Phase 5).
  • The global pilot registry and reconciling a Director's local pilots into stable cross-event identity on sync (Architecture §9).

Open decisions

  1. One-way push protocol. Offset / acknowledgement mechanics, batching, how a Director authenticates to the Cloud, and exactly-once vs at-least-once semantics on resume. Builds on the append-only log's resumable-sync property (Architecture §3).
  2. Warehouse schema & storage strategy. Whether the Cloud stores raw logs, projections, or both; how events from many Directors and chapters are partitioned; retention.
  3. Season / championship model. How events link into a season, the configurable scoring systems (points, drops, qualification pathways), and where season standings are computed.
  4. Global pilot registry & identity reconciliation. How local event pilots merge into a stable global identity on sync — claiming, dedupe, and conflict handling — without ever blocking an offline race.
  5. Account model for off-LAN viewers. What an account is, and how it maps to the read authorization defined in the Protocol spec.
  6. Two-surface deployment. Whether the live relay and the long-term portal are separate virtual hosts (dynamic realtime vs heavily-cached / mostly-static). Architecture calls this an ops decision, not an architectural one.
