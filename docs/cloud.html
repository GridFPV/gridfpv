Cloud & Season

Internal design doc · the optional relay, the warehouse, and the cross-event season layer

The optional Cloud: an off-LAN relay for live events, a long-term warehouse for the accumulated history, and the cross-event season / championship layer. It receives a one-way, resumable push of each Director's append-only log and serves the same protocol off-LAN. It is never authoritative over a live race and never sits in the timing critical path.

This doc owns the Director → Cloud push, the warehouse (aggregating many events' logs), the two Cloud surfaces and their component library, the season model, the global pilot registry / identity reconciliation, and the off-LAN viewer account model. It builds on the append-only spine and resumable sync from Architecture §3, the Cloud shape in §8, and the trust boundaries in §9; it deepens the season phase from Event Pipeline Phase 5 and Pipeline: Season. Wire-level message shapes and the read-authorization contract belong to the Protocol spec; we reference them rather than redefine them. Harder specifics are parked as Open decisions. When this doc and the Vision disagree, the Vision wins.

1. What the Cloud is — and is not

The Cloud is the optional second transport for the one protocol. Everything it serves is derived from logs the Directors produced; it adds reach and longevity, never authority. The Cloud software is FOSS and self-hostable: a chapter can run its own hosted instance just as the project runs a SaaS one. The hosted SaaS is simply one instance of that same software, not a separate proprietary product.

Never authoritative over a live race; never in the live path. Truth for an event is the Director's append-only log. The Cloud only ever receives that log and serves read/realtime projections from it. If the Cloud is down, slow, or absent, every race still runs and is still recorded — nothing on race day depends on it.

Self-hostable; accounts are built into the software. The Cloud is FOSS and any party can host an instance — a chapter's own self-host or the project's SaaS. Accounts are a built-in feature of the Cloud software, not a SaaS-only add-on: every hosted instance has accounts, because the account model ships in the same server crate. The SaaS is just one such hosted instance among many.

Same server crate, different storage trait. The Cloud reuses the same Rust (Tokio + axum) server crate the Director embeds. The only swap is the storage implementation behind a trait — SQLite per-event on the Director, Postgres in the Cloud (Architecture §2). The read/realtime contract is therefore literally the same code on both transports, so clients can't tell which they're talking to.

Authoritative only for what only it can see. The Cloud is the authoritative aggregate for cross-chapter projections — global career stats and multi-chapter season standings — because no single Director has the other chapters' logs. That authority is over derived projections assembled from many events' logs, not over any event's truth (see §5, §6). A Director remains authoritative for its own events and can compute a fully-local season over them with no internet.

One Director ↔ one Cloud is an assumption, not a decision. Everything below describes a Director relating to a single Cloud instance. Whether an RD can federate one Director to several Cloud instances at once — given the Cloud is FOSS and self-hostable — is an open question (§8): unresolved, and flagged here so the single-Cloud framing throughout this doc is read as provisional.

2. The one-way resumable push

A Director with internet ships its append-only log to the Cloud as it grows. The design falls straight out of the spine: the log is an ordered, append-only sequence, so syncing it is streaming an offset forward, never reconciling divergent state.

Sync is an offset, not a merge. Each event log entry has a monotonic, gap-free offset within its event. The Director streams entries from the last offset the Cloud acknowledged; the Cloud appends them in order and acknowledges the highest offset it has durably stored. There is no conflict resolution because the flow is one-way and the order is fixed by the log (Architecture §3).

The loop

  1. Authenticate & identify the stream. The Director opens a session to the Cloud (see authentication below) and names the stream it is pushing — an (event id), globally unique, minted by the Director when the event is created.
  2. Ask for the resume point. The Cloud replies with the highest contiguous offset it has durably stored for that event (0 for a new event).
  3. Stream batches forward. The Director sends entries from that offset in contiguous batches (offset-ordered, bounded by count or bytes), and keeps streaming as the live log grows.
  4. Acknowledge durably. The Cloud appends a batch, then acknowledges the new high-water offset only after it is committed to Postgres. The Director advances its "last acked" cursor.
  5. Resume after a drop. On reconnect, go back to step 2. Because the Cloud reports its durable high-water mark, the Director simply re-streams from there.

Delivery semantics

At-least-once on the wire; exactly-once in effect. A drop between "Cloud committed" and "Director saw the ack" causes the Director to re-send an already-stored batch on resume. That is fine: because every entry carries its log offset and the Cloud stores the log keyed by (event id, offset), a replayed entry is an idempotent upsert — same offset, same bytes, no duplicate. So the transport is at-least-once, but the warehouse is exactly-once by construction. This is the same dedup-by-offset property that makes adapter reconnects safe (Timer Adapters §5), one tier up.

Two invariants make that hold: entries are immutable once written (the append-only rule — corrections are new higher-offset entries, never edits, per Architecture §3), and the Cloud only ever advances a contiguous high-water mark, so a gap can never be acknowledged. A mismatch between a re-sent entry and the stored entry at the same offset is therefore impossible in normal operation and is treated as corruption to surface, not to merge.

How a Director authenticates to the Cloud

Pushing is a write into the warehouse and so is privileged — distinct from the open/lightly-tokened reads on the LAN (Architecture §9). A Director holds a Cloud credential, obtained once when its operator links the Director to a Cloud account / chapter, and presents it to open a push session. The credential authorizes which streams this Director may push (its own events, scoped to its chapter), so one Director can't write into another's history. Exact credential format, rotation, and the linking handshake are the Protocol spec's job; the commitment here is: push is authenticated, scoped to the pusher's own events, and one-way.

IRLThe push commonly rides venue wifi or even a phone hotspot mid-event — so it must tolerate flaky, intermittent links and resume cleanly. It is the primary broad-visibility path, not the LAN (Architecture §7).

SimThe Director usually already has internet, so the push is typically continuous and live — a sim league's whole audience watches through the Cloud relay.

3. The warehouse

Where the Director keeps one SQLite file per event (the file is the event), the Cloud aggregates many events' logs — across classes, chapters, and Directors — into one Postgres store. It is the third storage tier from Architecture §4. The container shape this builds on — an events table plus an event_log table keyed (event_id, offset) with the fact as JSONB — is the Cloud storage realization sketched in Architecture §4; this section adds the warehouse-scale concerns (aggregation, partitioning, retention) on top of it.

Raw log vs projections

Store the raw log; treat projections as a derived cache. The warehouse persists the append-only log entries as the durable, authoritative-for-the-Cloud record, exactly as received. Projections — heat results, event standings, career stats, season tables — are computed from those logs and stored as materialized projections for fast reads, but they are always recomputable and never the source of truth. This is the spine's central promise (Architecture §3): a new career metric is a new projection over existing history, not a migration.

Keeping the raw log is what lets the Cloud serve open data honestly, recompute after a late marshaling correction syncs up, and add metrics retroactively — the same guarantees the Director has, at warehouse scale. The projection layer is the same projection engine code the Director runs, fed from the Postgres-backed storage trait.

Aggregating, partitioning, retention

Aggregation boundary
The natural unit is still the event: its log is stored as a contiguous offset-ordered sequence keyed by (event id, offset). Cross-event projections (career, season) fold over many such sequences. Events roll up to chapters (and to a global scope) for the portal's aggregate views.
Partitioning
Per-event logs are append-heavy and grow without bound across a chapter's history, so the raw-log table is the obvious partition target — by event, and/or by time. Recommended default: partition the raw log by event (each event self-contained, easy to detach/archive), with time-range sub-partitioning available for very large or long-lived chapters. Projection tables are comparatively small and queried by pilot / class / season, so they index rather than partition.
Retention
Two tiers with different policies. Raw logs are the long-term open-data asset and are kept indefinitely by default; cold/archived events can be detached to cheaper storage while staying replayable. Live-relay state (the hot, realtime projections for an in-progress event) is ephemeral — it exists to serve the live surface and can be evicted once the event concludes, since it is rebuildable from the log. Heavy signal-context attachments (RSSI history, IRL only) are the bulk of the bytes and may warrant their own retention/sidecar policy — tied to the open decision in Timer Adapters §9.

4. The two surfaces, one component library

The Cloud exposes two surfaces (Architecture §8) that share one component library but have opposite scaling profiles.

The live relay
The same one-protocol PWA the Director serves on the LAN — realtime, single-event, latency-sensitive, written once and run on either transport. It reads the hot projections for an in-progress event and pushes change frames over WebSocket. Scales with concurrent viewers of live events; favors fan-out, low latency, and sticky/realtime connections.
The long-term portal
Career profiles, season / championship standings, open-data dashboards, and embeddable widgets — Cloud-only by nature, because the Director only knows one event and this reads the accumulated warehouse. Read-heavy, highly cacheable, mostly slow-moving content; scales with total catalog size and crawler / embed traffic, not live fan-out.

One component library, two scaling shapes. The frontend building blocks (leaderboard, bracket, pilot card, lap table) are shared so a career page and a live overlay look and behave like one product. What differs is the serving profile: the relay is dynamic realtime; the portal is cache-friendly read.

Because they scale oppositely, splitting them into separate virtual hosts (a dynamic realtime host vs a heavily-cached, possibly near-static stats host) is a reasonable deployment choice — but an optional ops decision, not an architectural one (Architecture §8). Both are the same server crate over the same warehouse; the split is about cache and scaling policy, not about two codebases.

5. The season / championship model

A season links several independently-run events into a championship and computes standings across them, per class (Pipeline: Season). Events are run independently and need not know about a season while they run — the season references them and folds their results afterward, so seasons never touch the live path.

Season
Name; scope (per class, possibly per discipline); the set of member events by reference; the scoring config (scheme + tiebreakers + drops); qualification rules.
Scoring config
Configurable with presets: finishing-position points per event, best-N-of-M (drop your worst events), or cumulative total; configurable tiebreakers; optionally participation / attendance points and minimum-events thresholds.
Qualification pathway
Cutoffs / thresholds that promote pilots from a season into a championship — the Global-Qualifier → championship analog — modeled lightly here.
Season standing (projection)
Per pilot per class: aggregated points, events counted (after drops), rank. Derived, recomputable, never authored.

Standings are a projection — computed where the logs are. A Director computes a season over its own events, fully offline — a self-hoster runs a local league with no internet. The Cloud computes the cross-chapter / global season because only it holds the other chapters' logs; it is the authoritative aggregate for those broader standings. Both run the same projection logic; they differ only in which logs they can see.

BothScoring is identical — points are points. Sim leagues and IRL chapters aggregate the same way; whether a season is per-discipline or may mix sim and IRL is a configuration choice (open decision).

6. Global pilot registry & identity reconciliation

Career and season stats only mean something if they accrue to one person across events. The Cloud holds a global pilot registry of stable cross-event identities; the Director runs with purely local pilots and reconciles them to global identity on sync. This is the cross-event half of identity from Architecture §9.

Identity never blocks an offline race. Registration binds a timer's local reference (node seat, sim player name) to a local pilot — that's all a race needs. Mapping a local pilot to a global identity happens on sync, after the fact. A venue with no internet runs entirely on local pilots and reconciles later; nothing about global identity is on the race-day critical path.

Reconciliation is a three-step problem, handled when a Director's log reaches the Cloud:

Claim
A pilot (or the RD on their behalf) asserts that a local pilot in event X is a given global identity — e.g. via a self-registered account, a MultiGP id, or an RD confirmation. A confident claim links the local pilot to the global registry entry.
Dedupe
Suggest likely matches for unclaimed local pilots — same display name, same external id (MultiGP / sim handle), recurring across a chapter's events. Surface candidates for confirmation; never auto-merge silently across people, since a wrong merge corrupts career stats.
Conflict
When evidence disagrees (two locals claim one identity; one local matches two globals), route to a human (the pilot or chapter admin) to resolve. Because identity is a projection over the logs plus a mapping table, a resolved or reversed merge just recomputes the affected career / season projections — nothing in the underlying logs changes.

Mapping is data, not log mutation. The global identity for a local pilot lives in a registry mapping the Cloud owns, not by rewriting any event's log. That keeps each event's log self-contained and replayable, and makes any reconciliation reversible by recompute — consistent with append-only truth.

7. Account model for off-LAN viewers

On the LAN, reads stay open or lightly tokened to anyone present (Architecture §9) — the LAN stays open, and this account gate is Cloud-only: offline-first can never require a Cloud account. On the Cloud, reads require a free account; the Cloud authenticates accounts to gate reads, and no race is ever controlled through the Cloud.

Open, but signed in — a free account, not a paywall. Reading on the Cloud requires an account, but the account is free, and any account-holder gets the full open, queryable, exportable data: the open-data API and bulk export are available to any member, and a pilot's own data stays portable to them. Data stays open to members; this is "open, but signed in," not a wall in front of the data. The LAN remains fully open with no account at all.

Accounts gate reads; control never leaves the Director. A Cloud account identifies an off-LAN viewer and maps to the protocol's first-class scoped read tier — the same tier the LAN's open / join-token reads use (Protocol §5). The privileged control role (race control, marshaling, configuration) exists only on the Director and is never granted by a Cloud account.

Mandatory TLS — zero unencrypted traffic over the internet, ever. Everything the Cloud serves or receives over the public internet — account auth, the read snapshot and change stream, and the Director→Cloud log push (§2) — travels over HTTPS / WSS end-to-end, always. There is no plain-HTTP Cloud mode and no exception for convenience on a public address. This is a hard, non-negotiable requirement enforced in the architecture, not a recommendation (Architecture §9; mechanics in Protocol §5). It contrasts with the trusted LAN, where plain HTTP is acceptable because the network is trusted and loopback control carries no credential at all.

Accounts serve a few concrete needs beyond plain viewing:

  • Reach & visibility scoping — most live and historical data is open-data to any account-holder, but some chapters may want private or pre-publication events visible only to specific linked accounts. The account maps onto the protocol's read-authorization scopes.
  • Pilot self-claim — an account is how a pilot claims their global identity (§6) and owns their career profile.
  • True push notifications — installability and web push ride the Cloud's HTTPS transport (Architecture §7), so an account is the natural subscription anchor for "your heat is up" alerts.
  • Director linking — an operator account is what a Director links to in order to obtain its push credential (§2).

The one anonymous exception is embeddable public widgets, which are a per-chapter opt-in: a chapter may choose to expose a public widget that renders with no account, so it can embed a leaderboard or bracket on its own site. Otherwise Cloud reads require the free account described above — but because the account is free and grants the full open dataset, accounts add claim, scoping, and push on top without becoming a wall in front of open data.

8. Open decisions

  1. Accepted — Push transport & batch shape. Push over the protocol's WebSocket transport with offset-acked batches, as recommended. Open refinement: batch sizing (count vs bytes vs time), backpressure, and how aggressively to push mid-event on a flaky hotspot — tune batch size to the link.
  2. Accepted — Push-credential mechanics. A per-Director, chapter-scoped push credential issued at link time, as recommended. Open refinement: credential format, rotation, and the Director-to-Cloud linking handshake (shared with the Protocol auth design).
  3. Accepted — Global offset / event-id scheme. UUID event ids minted by the offline Director, with offsets kept per-event, as recommended. Open refinement: whether to additionally lift offsets to a per-chapter global sequence in the warehouse.
  4. Accepted — Warehouse partitioning & retention. Partition the raw log by event, kept indefinitely as the open-data asset, as recommended. Open refinement: time sub-partitioning for very large chapters, the archive/detach policy for cold events, and a distinct retention/sidecar policy for heavy IRL signal-context (ties to Timer Adapters §9).
  5. Accepted — Projection materialization in Postgres. Projections are materialized but always recomputable from the raw log, as recommended. Open refinement: which projections are materialized vs computed on read; incremental maintenance vs scheduled recompute; and how the shared projection engine is parameterized for warehouse scale.
  6. Accepted — Two-surface deployment. An optional two-host split of the live relay and the long-term portal (dynamic realtime vs heavily-cached / near-static), as recommended. Architecture §8 calls this an ops decision, not an architectural one.
  7. Resolved — Season scope. Season scope is configurable — the default is per-class, but a season may span classes or mix sim + IRL where a league wants a combined championship. Open refinement: when both the Director and the Cloud compute a season, how the local view and the authoritative Cloud aggregate are presented together (carried from Pipeline: Season).
  8. Accepted — Qualification & participation modeling. Qualification is modeled lightly, leaving most championship-qualification logic to the league, as recommended. Open refinement: attendance / participation points and minimum-events thresholds.
  9. Accepted — Identity-reconciliation policy. Claim / dedupe / conflict with no silent cross-person merge, as recommended. Open refinement: the confidence thresholds for auto-suggesting merges, what evidence counts as a confident claim (MultiGP id, verified account, RD confirmation), and the conflict-resolution authority (pilot vs chapter admin vs Cloud).
  10. Resolved — Account model & read scoping. Cloud reads are free-account-gated — a free account is required to read on the Cloud, and any account-holder gets the full open, queryable, exportable data ("open, but signed in"); the LAN stays open and embeddable public widgets are a per-chapter opt-in (§7). Open refinement: how the account maps onto the protocol's read-authorization scopes, and which chapter data is private / pre-publication vs the open-data default (shared with the Protocol spec).
  11. Open — Multi-cloud / federation (no decision yet). §1–§7 assume a Director links to one Cloud. But the Cloud is FOSS and self-hostable, so an RD may legitimately want to federate a single Director to several Cloud instances at once — the project SaaS, a league/community-run instance, and a chapter's private self-host — pushing and reading selectively per instance. This fits the project's FOSS ethos and is unresolved & deliberately deferred. It ripples through several decisions above: the per-Director push credential (§2) becomes per-(Director, Cloud) with per-target selection, batching, and dedup; identity reconciliation (§6) and the global pilot registry must reconcile across independent clouds with no single authority; season aggregation (§5) and the account model (§7) may differ per instance, and a pilot/viewer may hold accounts on several. Captured now so the single-Cloud assumptions baked into §1–§7 are known to be provisional; path forward to be designed in a future session.
