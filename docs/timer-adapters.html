Timer Adapters

Internal design doc · the canonical event model and the one timing interface

The foundational wall. Every live timing source — Velocidrone, RotorHazard, LapRF, manual entry — sits behind one interface and is translated into the same small set of canonical events. This is the vocabulary the whole append-only log speaks, so getting it honest matters more than anything downstream.

This doc owns the canonical event model and the adapter interface for live timing sources. Leaderboard / results imports (a Velocidrone leaderboard, MultiGP results) are deliberately out of scope — they produce a ranking, not live observations, and belong to Qualifying / External Sync. When this doc and the Architecture doc disagree on shape, follow Architecture (§3 the spine, §9 identity); when either disagrees with the Vision, the Vision wins.

1. The principle

Timers are pluggable; Velocidrone and RotorHazard are the first two, built in parallel. Designing against the simulator keeps the abstraction honest — if the model only fits hardware, it's wrong — while RotorHazard is the first real-world target. Every source is an adapter behind one interface.

Adapters are pure translators. A source's input goes in; canonical events come out. Adapters hold no race logic, own no truth, and never block the engine — they translate and append. That purity is what makes them testable by replaying recorded sessions, and underpins the testing guardrail: tests never depend on a live, shared timing backend (the Velocidrone servers), though a self-hosted, disposable instance like dockerized RotorHazard is fair game — see Testing Strategy.

Observations in, derivations out. Adapters emit raw observations (a gate was crossed). They do not emit laps, results, or standings — those are projections the race engine derives (see Architecture §3). A "lap" is two consecutive passes, computed downstream, identically for every source.

2. The canonical event model

Adapters append a small, source-agnostic set of events to the log. Everything a source can tell us reduces to these:

AdapterConnected / AdapterDisconnected
The source became available or went away. Liveness for the RD; never affects past truth.
SessionStarted / SessionEnded
The source's own race/heat lifecycle, where it exposes one (Velocidrone race start/finish; RotorHazard race start/stop). Optional — declared by capability.
CompetitorSeen
A source-local competitor reference appeared (a node seat went active, a sim player joined the room). Feeds auto-presence and the binding step — but the binding itself is a registration action, not an adapter event (Architecture §9).
Pass (the atom)
A gate crossing — the one observation everything else derives from. Fields below.

A Pass carries:

  • source / adapter id — which timing source produced it.
  • local competitor ref — the source's own handle (node seat, sim player name, transponder id), later bound to a GridFPV pilot.
  • source timestamp — in the source's own clock (see §4), plus a monotonic sequence number where the source provides one.
  • heat tag (D20) — the adapter leaves it empty; the bridge sink stamps the running heat at append, and every fold attributes the pass by tag (positional attribution is the legacy fallback). Once a heat's result is Final, late passes are frozen out of its window entirely.
  • gate / split index — optional; defaults to the lap gate. Present for sources that report multiple gates or splits (Velocidrone).
  • signal context — optional; RSSI peak / stats, enter-exit window, or a reference to captured signal history. Present only where the source has it (§3).

3. Granularity & signal context

Sources differ sharply in how much they reveal beneath a pass, and the model must be honest about that rather than assume the richest case.

The pass is the universal atom; signal context is optional. A simulator reports an exact crossing with nothing underneath — there is no RSSI, no threshold, nothing to re-derive. Hardware reports a crossing plus the signal that produced it. The canonical Pass therefore treats signal context as an optional attachment, never a requirement.

Consequence: "recover a missed lap from signal history" is a hardware-only capability — it's meaningful for RotorHazard/LapRF and impossible (and unnecessary) for a sim, whose detection is already exact. The model accommodates both without special-casing: marshaling that re-derives from signal is simply unavailable on adapters that declare no signal capability (§5).

IRLPass + RSSI/threshold context; laps can be recovered or re-timed from captured signal.

SimPass only, exact; nothing to recover — a missed lap means the game didn't report a crossing, full stop.

4. Clocks & time

Every source stamps in its own clock — game-engine time (Velocidrone), server time (RotorHazard), device RTC (LapRF), wall clock (manual). The model keeps these straight rather than flattening them on arrival.

Source time is authoritative for intervals; arrival time is metadata. Lap and split durations are computed from the source's own timestamps, which are internally consistent and immune to network jitter. The Director also records each event's arrival time — but only for ordering and liveness, never for timing math.

At session start an adapter captures an offset mapping its source clock onto the Director's session timeline, so events from different sources (and the Director's own clock) can be ordered and displayed on one axis. Where a source exposes a monotonic sequence counter, the adapter carries it through — it disambiguates passes that share a timestamp and survives clock adjustments.

This is realized as a per-source ClockAlignment captured at the session anchor (mapping source → session time onto a shared SessionTime axis), used strictly for ordering/display — intervals always use the source clock. Passes are ordered by a single rule — present sequence first, then source timestamp — shared with the lap projection, so the whole system orders passes identically.

5. The adapter interface & capabilities

An adapter does three things: connect to its source, translate source input into canonical events, and declare what it can do. The last point is how IRL/sim divergence stays out of the engine: instead of the engine asking "is this a sim?", it asks the adapter "do you support calibration / signal / frequency management?" and adapts the UI and marshaling accordingly.

CapabilityVelocidroneRotorHazardLapRFManual
Live passes✓✓✓✓ (entered)
Gates / splits✓~ (single)~ (single)✗
Signal context (RSSI)✗✓✓ (stats)✗
Calibration (enter/exit)✗✓~✗
Signal-based lap recovery✗✓~✗
Frequency / channel mgmt✗✓✓~
Source race lifecycle✓✓~✗
Race control (accepts start/stop)✓ (host only)✓~✗
Seating (accepts a lineup)~ (select-only)✓~✗

Capabilities are reported, not static per kind (decided 2026-08-29). The last two rows are why: Velocidrone's race control and seating exist only while the Director's machine is the multiplayer room host — the same adapter degrades to observe-only otherwise — and RotorHazard's set differs socket-only vs plugin (PluginHello.advertises is the working precedent). So the capability declaration lives in the timer's live reported status (alongside TimerStatus/PluginPresence), and the engine/console consult the report — never the kind. Race control means the source accepts a commanded start/stop; it is distinct from source race lifecycle, which only means the source reports its own start/finish edges. Seating "select-only": Velocidrone's activate restricts the race to chosen lobby pilots but cannot add a pilot who is not in the room.

As built (v0.4) — the seam gap. The Capabilities declaration exists (crates/adapters/src/lib.rs, seven flags, serde-ready) but is dead code outside the adapters crate: nothing reads capabilities() at runtime, there is no TS binding, and the de-facto capability check is match timer.kind (~10 RH-named route guards in crates/server/src/app.rs). There are also two runtime seams, neither general: LapSource::run_heat (sim-shaped, implemented only by the Mock) and the bespoke RhConnection driver (persistent-connection-shaped, RH-typed throughout) — and PassSink::emit hard-codes GateIndex::LAP, so a split cannot survive the bridge. The agreed build order when Pillar 4 opens this seam (research 2026-08-29): 1) promote Capabilities onto Timer/the wire and convert the kind guards to capability refusals, 2) lift RhConnection's arm/disarm/prepare/drain skeleton into a kind-agnostic TimerConnection with capability-gated prepare/tune/seat/start, 3) add TimerKind::Velocidrone { url }, 4) bind identity by ref via CompetitorSeen (Velocidrone keys on stable player uid, not RH's positional node-{n} remap).

An adapter never owns truth and never blocks: it appends observations and the Director proceeds. A source that drops mid-race reconnects and resumes appending; deduplication relies on source sequence numbers / timestamps so a reconnect can't double-count a pass.

Channel capability is part of what an adapter declares. Beyond the yes/no “frequency / channel mgmt” row, an adapter that manages channels declares how: a fixed capability (only a built-in allowed set of channels) or a flexible one (the standard FPV channel catalog plus arbitrary custom raw-MHz, as RotorHazard allows), together with its node/slot count. The standard catalog is built-in; what a given timer can actually tune to lives in that timer's config. The race engine assigns channels from this declared set (first-fit + RD override), capped by the node count, and the adapter dynamically tunes its nodes to the assignment at race time (Race Engine §5, Setup). Sim sources declare no channel capability. As built (v0.4), this is the Timer-registry model (#73/#117): channels are configured on the timer, not on the event — and crucially a timer's available channels can exceed its node count. The full model (channels ≠ nodes, the standard catalog, Fixed/Flexible, static vs per-heat assignment) has its own deep dive: Channel Model.

6. Identity binding

Each source speaks in its own local references — a node seat, a sim player name, a transponder id. Binding those to a GridFPV pilot is a registration action (Architecture §9), not something the adapter decides; the adapter only reports the local refs it sees (CompetitorSeen), which for sim drives auto-membership — auto-adding seen players to the class roster (membership = presence) and auto-binding name matches ("everyone in the room at 8 PM gets bracketed") — and gives the RD the list to bind against (Setup).

7. Velocidrone — the first adapter

Built first, on purpose. Velocidrone exposes a WebSocket feed (opt-in: Options → Main Settings → Websocket Communication → Yes) carrying gate passes, lap splits, lap times, race totals, and holeshot/spread straight from the game engine. Concretely (validated against two open-source consumers — the rh-velocidrone plugin and VelocidroneWebSocketConsumer) it is a raw WebSocket — not Socket.IO — at ws://<host>:60003/velocidrone, carrying one-key JSON frames: racestatus (lifecycle), racedata (a per-crossing telemetry snapshot keyed by player name, whose time is cumulative game-engine seconds), and pilotlist (roster), plus an empty-string keep-alive ping. Mapping it to the canonical model:

Passes & splits
Each gate crossing becomes a Pass with its split/gate index. The lap times and totals the game also reports are treated as advisory — the engine derives laps from the pass stream so every source is scored identically, and the provided totals are a cross-check.
Clock
Game-engine time is the source timestamp; intervals come from it directly. Velocidrone exposes no monotonic sequence counter, so its passes carry none and dedup falls back to (source, player, source-timestamp) — safe because time is unique per crossing.
Identity
The sim player name is the local ref reported via CompetitorSeen.
Capabilities
Live passes ✓, splits ✓, source lifecycle ✓; signal ✗, calibration ✗, frequency ✗. No special-casing — the adapter simply declares this, and the UI hides calibration and signal marshaling for it. Race control and seating are declared conditionally: present while the Director is room host, absent otherwise (§5).

Verified against the local RE workspace (2026-08-29) — the authoritative sources are the maintainer's own reverse-engineering projects (~/development/fpv/velocidrone/: the binary-derived velocidrone-websocket/docs/ws-spec.md and velocistream, whose devel branch ran the full seat → start → ingest → results loop against the live sim), never community tools. Key facts, with the receipts in velocistream@devel's controller tests:

The protocol is bidirectional. startrace, abortrace, activate([uids]), getpilots (and lock/camera controls) all work — but are host-gated and fail silently: a non-host command is a no-op with no error. Detect host status via player.raceManager; per the RotorHazard rule, prove the write landed — infer startrace success from the subsequent racestatus/countdown, match getpilots → pilotlist with a timed wait.

Wire traps, all verified: booleans arrive as strings ("True"/"False", capitalized — C# bool.ToString()); racedata.time is cumulative float seconds as a decimal string (not the spec's "01:23.456"); FinishGate.StartFinishGate is a persistent track-shape flag, not a crossing event, and lap detection must branch on it (both branches have exact-ms tests — port that logic, don't re-derive it); a pilot's first racedata appearance is the holeshot; no session event in single player (a multiplayer room is required for the full model); practical heat cap ~10 pilots; a 40 s server timeout needs an app-level keep-alive; and the RE library's default service path /ws/ is wrong — the endpoint that has actually connected is ws://<host>:60003/velocidrone/ (which this repo's transport already uses).

Statically resolved from the 1.17.13 binary (2026-08-29, dnre-mcp over the maintainer's Managed drop; full spec rewritten in the RE workspace's ws-spec.md): every server→client message is a BINARY WebSocket frame (opcode 0x2) carrying UTF-8 JSON — the game never sends text frames, so this repo's text-only transport read drops the whole feed against a real game (KNOWN BROKEN note in velocidrone/transport.rs; the #483 fix). The raceAction vocabulary is exactly "start"/"abort"/"race finished" (velocistream was right; the old spec's "started"/"aborted" don't exist in the binary). racedata.uid is a bare JSON number on 1.17.13 (string in pilotlist/ActivateError); gate is the 1-based per-lap checkpoint ordinal of a packed lap*1000+gate progress counter; snapshots are whole-field, per crossing, throttled to 10 Hz; ActivateError fires per missing uid in request order (the seating readback); SocketManager serves only the newest connection (an older client silently starves); multiplayer countdown runs 5→0; a new 60 Hz all-numbers imu frame family (opt-in, Betaflight-only) must be tolerated; and the keep-alive is {"command":"ping"} every ~5 s against a 40 s sliding idle timeout. The wire-faithful mock is gridfpv_testkit::vd_mock / cargo xtask vd-mock, self-tested in plain cargo test and replaying a genuine 134-frame capture.

Host mode is required for the 1.0.0 core loop (decided 2026-08-29) — see §9. Operationally the maintainer runs a dedicated Velocidrone account for the Director to host and spectate with, separate from the racing accounts.

Why this keeps us honest: Velocidrone has no RSSI, no thresholds, no frequencies, and a clock that isn't ours. If the canonical model handles it cleanly as a first-class source — and it does — then hardware, which is a superset, fits without strain.

8. Other sources (sketch)

As built (v0.4) — the timer model & connection lifecycle. A timer in the registry is one of two kinds: Mock (a synthetic source — laps and lap_ms drive fake passes; seeded with the 8-seat Raceband grid) or RotorHazard { url } (a real RH server base URL). A RotorHazard timer connects when it is selected for the active event and stays connected (it does not connect only while a heat runs); a persistent driver maintains the link and reconnects with backoff, surfacing a TimerStatus of Ready / Configured / Connecting / Connected / Disconnected / Error. RH support is gated behind the Director's --features live build. At the heat's Stage transition the bridge prepares RH (tunes nodes, zeroes the current format's staging delays for an instant start, resets to READY) and seats a fresh RH heat with the bound pilots (RH's pass gate rejects crossings on unseated nodes); at Armed → Running — Grid's go — it emits a single stage_race. Because seating can switch RH's effective format to the seated heat's class format, the instant-start prepare is re-run right before the stage; a stage a busy RH drops ("status is not 'ready'") is retried every 5 s inside the ~15 s settle; and lap records are gated on RH confirming RACING for this arming, so a replayed previous-race snapshot can never contaminate the new heat. Every (re)connect also probes the GridFPV plugin handshake (missing / present / incompatible, surfaced on the timer row). With multiple timers selected, all stay hot-standby-connected and only the active source's passes feed the log — primary-preferred, non-sticky failover (#112); the switchover window is not yet buffered (a known deferred gap). Leaving Running disarms the race but keeps the connection alive.

Direction (2026-06-26) — the RH integration becomes a required GridFPV plugin (D16). The socket-only path described here works against stock RH but is limiting: the dense per-tick signal needs a save-then-pull, staging is zeroed with an alter_race_format hack, seating needs an add_pilot/alter_heat dance, and the ~0.9 s prestage can't be zeroed. The decided direction is a required GridFPV RotorHazard plugin running inside the RH server with RHAPI access (node manager / race events / config). The plugin makes those workarounds native — live dense RSSI (no save-then-pull), clean start/stop bypassing the RMS staging, per-node passes without the seating dance, and threshold/calibration access (unblocking the re-detection "recalculate" marshaling feature). It reuses RH's proven stack (node firmware + RMS + detection); GridFPV owns start/stop timing while RH owns start/stop/get-data. "Required" is a guided one-step install, not a hard-fail. The plugin supersedes the socket workarounds and becomes the primary RH integration. It also replaces the dropped own-the-stack timer-server (D15, superseded).

Status (v0.4.0-alpha.1): the design lives at RotorHazard Plugin; the plugin itself ships in-repo (plugins/gridfpv/), is served by the Director at GET /plugin/gridfpv.zip (embedded at compile time so the bundle always matches the Director), and installs via the guided one-step flow. Shipped capabilities: hello (versioned handshake), live_signal (incremental dense RSSI, suppressing the save-then-pull), live_pass (native per-node passes, deduped against current_laps). Clean start/stop ownership and calibration write-back are the remaining slices; until then the Stage-time socket prepare/seat flow above IS the production control path.

RotorHazard
Socket.IO / RHAPI; the full-signal case, with calibration and signal-based recovery. Validated against a live dockerized RotorHazard with 8 mock nodes (see docker/rotorhazard/). The authoritative pass source is current_laps — a full snapshot re-sent on every update ({current:{node_index:[{laps:[{lap_number, lap_raw, lap_time, lap_time_stamp, …}]}]}}, outer array index = node index, lap_time_stamp in cumulative ms since race start) — which the adapter diffs per node, emitting a Pass only for genuinely new laps. Per-pass RSSI comes from node_data.pass_peak_rssi[] (not the lap record) and annotates the pass's signal context. A pass_record {node, frequency, timestamp} fires per crossing but is an advisory cross-check only — its epoch-ms timestamp is a different clock from the race-relative lap_time_stamp, so no pass is minted from it. race_status is an integer (3=staging, 1=racing, 2=done, 0=ready); the transitions into racing/done are the session start/end edges, and the per-node lap_number is carried as the pass sequence and anchors dedup. Built in parallel with Velocidrone as the first real-world target; the dockerized RH both feeds recorded fixtures and is allowed for live integration tests (a local class — Docker required). The harness builds RotorHazard v4.4.0 from source (the cruwaller image went stale at 4.0.0-beta.4; MOCK_NODE_SIGNAL=1 required) with 8 mock nodes, attached via the timer's URL; the test driver emits stage_race over Socket.IO and injects passes with simulate_lap {node}, bypassing signal detection (see docker/rotorhazard/). The guardrail bans depending on a live, shared/production backend (concretely the Velocidrone game servers, which stay fixtures-only) — not all live timers.
LapRF
Binary protocol over serial/USB/TCP; PassingRecord (slot, RTC time, transponder id) and RssiRecord (RSSI min/max/mean) — passes with RSSI stats and a device clock.
Manual
The RD enters laps directly; the universal fallback. Passes with wall-clock timestamps, no signal, no calibration — proves the model degrades gracefully to the simplest possible source.

Each gets a full treatment when it's built; the sketches confirm the model fits them.

9. Open decisions

  1. Resolved — Signal-history storage. Hardware sources always store a per-pass signal summary (peak RSSI, enter/exit window) inline in the log. In addition, a bounded RSSI window around each pass is retained as an event-local sidecar — not pushed to the Cloud by default — so a missed lap can be re-derived. Pairs with the storage tiers in Architecture §4. Implemented today: a per-pass rssi_peak, coarse streamed SignalChunk traces + SignalThresholds (enter/exit levels), and the dense per-tick SignalHistory — live via the plugin's gridfpv_signal, or the post-race save-then-pull on stock RH.
  2. Resolved — Multi-gate / split track model. A track is modeled as ordered gates per lap; a Pass carries a gate index. A lap is a start/finish-gate crossing and splits are sector times; the default is a single gate.
  3. Resolved — Calibration model. Per-pilot enter/exit calibration is represented as logged adapter config, fed by the Practice calibration window. Hardware-only.
  4. Resolved — Reconnect / resume & dedup. Passes are idempotent, keyed on (source, sequence#) — or (source, local-ref, source-timestamp) where no sequence counter exists. On reconnect the adapter buffers and de-dups against those keys, so a resume can't double-count or lose passes.
  5. Resolved — Frequency / channel management ownership & model. The race engine allocates channels — it knows the heat/field and avoids conflicts — while the adapter advertises the hardware's channel capability (fixed allowed-set or flexible standard-catalog + custom raw-MHz) and node count, and applies the tuning dynamically at race time. Channels are defined on the timer (the Timer registry, #73/#117), not an event-level pool. Shared with the Race Engine; IRL sources only.
  6. Resolved — Velocidrone WebSocket message schema. Reconstructed and implemented from two independent open-source consumers (the rh-velocidrone plugin and VelocidroneWebSocketConsumer); a raw WebSocket at ws://<host>:60003/velocidrone carrying one-key racestatus / racedata / pilotlist frames (see §7). Since verified against the local RE workspace (2026-08-29): time is a cumulative float-seconds decimal string, and uid is on the wire in racedata. The raceAction vocabulary is conflicted between the workspace's own sources: the binary-derived spec settled "started"/"aborted", while velocistream's working consumer (and its tests) matches "start"/"abort"/"race finished" — parse tolerantly until resolved. Remaining unknowns (raceAction set, split-gate numbering, emitted decimal precision, keep-alive form — this repo's transport sends empty frames, velocistream sends {"command":"ping"}; #484 recommends the ping) are now resolvable statically: the maintainer supplies the game binary (.NET) plus his dnre-mcp tool, so the answers come from the decompiled current build rather than waiting on a live capture, with a live session as final confirmation. The full source reconciliation and mock plan live on #484.
  7. Resolved (2026-08-29) — Velocidrone control direction & host mode. The protocol is bidirectional but host-gated (§7). The 1.0.0 core loop requires the Director's machine to be the multiplayer room host, giving Grid the same ownership it has over RotorHazard: command the start, push the seating (activate). Observer mode declares its reduced capabilities honestly and degrades visibly; racing through it is post-1.0.
  8. Resolved (2026-08-29) — Capabilities are reported, not static. The capability declaration is part of the timer's live reported status (§5): Velocidrone's race control and seating flip with host status, and RotorHazard's set differs socket vs plugin. A static per-kind declaration would be wrong within the first hour of field use.
  9. Resolved (2026-08-29) — Gate index through the sink; split surfaces later. When Pillar 4 opens the seam, PassSink::emit gains a gate parameter so the bridge stops discarding data the log format already models — a one-line fix cheapest while the seam is open. Every split surface (UI, results columns) waits for the multi-timer work (#113), post-1.0, where splits are designed once for sim gates and physical split timers together.
