GridFPV

Clients

Internal design doc · the web clients of the one protocol — surfaces, framework, and shared frontend

Everything that renders GridFPV is a web client of the one protocol: the RD console in the Tauri window, the racer/spectator PWA, the OBS overlays, and (future) a privileged RD mobile-control surface on the LAN. They differ only in permissions, transport, and what they emphasize — not in how they talk to the Director. This doc settles the frontend stack those surfaces share and how they stay in lockstep with the Rust contract.

This doc owns the client surfaces, the frontend framework choice, the shared component library, the generated-types story, and PWA mechanics (install, offline shell, push, the LAN secure-context degradation). It builds on the contract in Architecture (§6 one protocol, §7 clients & connectivity) and defers what other docs own: the wire shapes and auth to Protocol; the broadcast subsystem — driving OBS, capture/RTMP, the overlay catalogue — to Streaming (here we cover only the overlay client: rendering and data); the Cloud transport, accounts, and push delivery infrastructure to Cloud & Season. The framework choice is decided (Svelte), and revisitable, and is also recorded in Open decisions. When this doc and the Vision disagree, the Vision wins.

1. Three surfaces, one client

Architecture §5 already says it: the RD console, the racer/spectator PWA, and the OBS overlays are "all the same kind of thing — a web client of the protocol. Only their transport and their permissions differ." This doc takes that seriously: there is one frontend codebase, one component library, and one set of generated types. A surface is a profile over that shared base — a different entry point, a different default permission posture, a different density — not a different application.

One codebase, profiled three ways. The surfaces are configurations of a single frontend — shared types, shared protocol client, shared components — not three apps. A bug fixed in the leaderboard fixes it everywhere; the contract can't drift between surfaces because there is only one client.

The RD console — control-oriented, dense, authenticated

The race director's cockpit, loaded inside the Tauri window (Architecture §2). It is the only surface that exercises the protocol's privileged write/control path — arming heats, marshaling, configuring the pipeline — so it authenticates with the RD role (Architecture §9; mechanics in Protocol). It is information-dense and keyboard-friendly: a working tool for someone running a live event, not a viewer.

The console is "just a co-located web client" (Architecture §2): it loads over the Tauri webview but talks to the same local axum server, over the same protocol, as everyone else. The Tauri shell buys a friendly native window and OS integration (file dialogs for export, single-binary packaging) — it does not buy a private back channel. Control authority is a protocol role, not a shell privilege.

The racer/spectator PWA — read-oriented, installable, push

The universal viewer (Architecture §7): the racer checking their next heat and standings, the spectator following the event. Read/realtime only — it never controls a race. It is a Progressive Web App so it can install to a phone home screen, keep an offline shell, and receive web push — though, crucially, only over the Cloud (HTTPS) transport (§4). It is the same web client that a future Capacitor wrap turns into a native app (§6).

IRLAt a field with no internet, racers join the Director's LAN and get live in-page updates over WebSocket — but no install and no true push (the LAN address isn't a secure context; §4).

SimAn online Velocidrone event is typically Cloud-reachable, so the same PWA installs and pushes normally — the sim case naturally lands on the HTTPS transport where full PWA features are available.

OBS overlays — read-only, lean, browser sources

Overlays are the broadcast-facing surface: staging, leaderboard, split-screen, podium, and bracket graphics loaded as OBS browser sources. They are protocol clients like any other (Architecture §10) — read-only, subscribing to the same realtime stream and rendering it. Their distinct needs are about rendering: transparent backgrounds, stable layout at a fixed canvas size, no chrome, and lean payloads so a machine already encoding video isn't taxed by the overlay.

Scope line with Streaming. This doc covers only the overlay client — how an overlay page subscribes, renders, and is told which race/class it shows. The broadcast subsystem — driving OBS scene switches, capture/RTMP handling, and the overlay catalogue/theming — belongs to Streaming. Overlays sharing the component library (the same leaderboard component the PWA uses, restyled for broadcast) is the seam between the two docs.

RD mobile-control surface — privileged, mobile, LAN-only (future)

Future surface. A second control client for the race director, mobile-optimized and exposed only on the LAN — never the Cloud. The use case: the RD is racing themselves, straps into their seat, and needs to start, abort, or advance the race from their phone without returning to the console. It is the same privileged write/control path as the console (mechanics in Protocol §5), just reached from a phone on the LAN.

Stricter authentication than the console. The co-located console gets its trust from living in the Tauri window on the Director's own machine; a phone on the LAN has no such standing and must prove itself. This surface therefore requires explicit RD login or device pairing — stricter than the console's ambient trust — before it can touch the control path. Control authority stays Director-only and LAN-only: this surface never widens who can control a race or over what transport, it only adds a mobile place to exercise the existing Director role.

2. Frontend framework — the decision

Architecture §11 parks this as "not load-bearing — every framework consumes the same generated types, to be settled with the client work." This is the client work, so we settle it: a decision with a clear rationale, explicitly revisitable, and recorded in Open decisions.

What's actually being weighed

FactorReactSvelte
FOSS contributor poolLargest — most front-end devs know itSmaller, but growing and well-liked
Ecosystem / off-the-shelf partsVast (component kits, tables, charts)Solid and sufficient; fewer choices

Decided: Svelte. The maintainer is a systems programmer (C/C++/Rust), not a frontend specialist, and the rest of the stack prizes leanness and a small footprint (Tauri over Electron for exactly this reason, Architecture §2). Svelte rewards that instinct: less framework ceremony and a syntax close to plain HTML/CSS/JS, which lowers the ceremony for a non-frontend maintainer; fine-grained reactivity that maps naturally onto a constant realtime change-stream; and a compile-away runtime that yields tiny bundles suiting lean OBS overlays and the LAN PWA. It matches the lean, single-binary Tauri ethos rather than fighting it. The contract is the same generated TypeScript either way, so the realtime/overlay work is comfortably within Svelte's reach.

The recorded alternative — React. React's edge is the larger FOSS contributor pool and ecosystem: the framework most front-end developers already know lowers the barrier to outside help, and its off-the-shelf parts (tables, charts, drag-and-drop heat editing) mean fewer wheels reinvented. If the project becomes contributor-driven rather than maintainer-driven, React's reach is the stronger argument — which is precisely why this stays revisitable, not locked. Switching is a bounded, known cost (see below), so React remains on the table at no surprise.

Why it's safe to defer/revisit. The contract is defined once in Rust and generated to TypeScript (Architecture §6); the protocol client is a thin transport-plus-subscribe layer; only the component library and surface entry points are framework-specific. Switching frameworks would mean re-authoring the UI layer, but not the contract, the transport behavior, or the Director — so the cost is bounded and known. We record Svelte as the chosen default and proceed; the decision is reversible at known cost, not a one-way door.

3. Shared component library & generated types

Two artifacts keep the three surfaces coherent: the generated types that define what the data is, and the component library that defines how it looks.

Generated protocol types
The wire types live in the Rust server crate and are generated to TypeScript (e.g. ts-rs) as a build step, per Architecture §6. Every surface imports the same generated types; a contract change in Rust ripples to a compile error in the frontend rather than a silent runtime drift. This is the mechanism that makes "one protocol" real on the client side. Generation cadence and CI checks are a Protocol-adjacent concern; the commitment here is that the frontend never hand-writes a wire type.
Protocol client
A thin, framework-agnostic layer: connect to a base URL, fetch a projection snapshot, subscribe to the WebSocket change stream, and expose typed state. It is configured only with a base URL, so it cannot tell LAN from Cloud (Architecture §6) — the same client code backs all three surfaces on both transports.
Component library
The reusable race-domain widgets — leaderboard, bracket tree, heat sheet, race clock, pilot card, standings table — built once and themed per surface. The PWA renders the leaderboard mobile-friendly; the overlay renders it transparent on a broadcast canvas; the console renders it dense beside controls. One component, three presentations.
Surface profiles
Each surface is an entry point that assembles components with its own permission posture and density. The console adds the control/marshaling components gated behind the RD role; the PWA and overlays omit them entirely (they never reach the privileged path).

The contract is generated, never transcribed. Wire types come from Rust; the frontend consumes them. The component library is the only place UI lives, so every surface shows the same data the same way unless it deliberately chooses otherwise.

4. PWA mechanics

The racer/spectator surface is a PWA so it can feel like an installed app where the platform allows it. Three mechanics, and one hard constraint inherited from Architecture §7.

Install
A web app manifest (name, icons, theme, display mode) lets the PWA install to a phone home screen or desktop. Install requires a secure context (HTTPS), so it is a Cloud-transport feature.
Offline shell
A service worker caches the app shell — markup, styles, scripts, the component library — so the UI loads instantly and survives flaky connectivity, with live data still arriving over WebSocket when connected. Service workers also require a secure context, so the cached shell is a Cloud-transport feature too. (The Director already serves the live app fine over LAN; this is about the installed/cached experience, not live viewing.)
Web push
"You're on deck," "your heat results are in," "the event resumed." Web push needs a service worker (secure context) and internet to reach APNs/FCM, so it rides the Cloud transport, HTTPS only. Push delivery infrastructure (subscriptions, vendor relays) belongs to Cloud & Season; this surface registers for and renders the notifications.

The LAN PWA is intentionally degraded (Architecture §7). A plain-HTTP LAN address is not a browser secure context, so service workers, install, and web push are unavailable on LAN — full stop. What still works on LAN is the part that matters live: opening the page and getting realtime updates over WebSocket, plus in-page alerts. Install, offline shell, and true push ride the Cloud transport (HTTPS). The same PWA code degrades gracefully — it feature-detects the secure context and simply doesn't offer install/push on LAN — so there is no separate "LAN build." A future native client (§6) is the path to LAN access and real push together.

5. Design system & UX

A modern, approachable UI for non-technical race directors is a stated Vision pillar and a differentiator against tools that feel like configuration panels. That ambition lives here.

Friendly to a non-technical RD. The person running an event may be a club volunteer, not an engineer. The console favors plain language, sane defaults, progressive disclosure (advanced settings tucked away), and confidence-building feedback — clear current state, obvious next action, reversible mistakes (which the append-only log makes literally true; Architecture §3). Density serves the expert without punishing the newcomer.

One design system, three contexts. A shared token set — colors, type scale, spacing, the brand palette already used in these docs — themes all three surfaces. The console is a dense desktop tool; the PWA is a calm mobile reader; the overlays are high-contrast, glanceable broadcast graphics. Same vocabulary, tuned per context, so the project reads as one product.

Accessibility and responsiveness are baseline, not polish. The PWA must work one-handed on a phone in daylight at a field; overlays must stay legible over video; the console must be keyboard-driveable for speed. The concrete design system — the token set, component states, the chosen component primitives (a headless kit vs. bespoke) — is deferred to design work and flagged in Open decisions, because it depends partly on the framework choice in §2.

6. Native deferral via Capacitor

Native apps are deferred but kept cheap, by deliberate symmetry with the Director (Architecture §7). The Director's RD console is a web UI wrapped in Tauri; the racer/spectator PWA can later be wrapped in Capacitor to ship a native app to the app stores. In both cases the web protocol-client is the constant, and the native shell is an optional enhancement, not a rewrite.

The web client is the constant on both ends. Tauri wraps the console; Capacitor would wrap the PWA. Neither shell forks the application — they package the same web client and add native capabilities (notably real push and LAN access together, the thing the LAN PWA can't have; §4). Native stays on the roadmap precisely because it cleanly resolves the secure-context degradation.

Because the PWA is already structured as install-aware and feature-detecting, the Capacitor wrap is incremental: reuse the build, swap web push for native push where the shell provides it, and gain LAN reachability without losing notifications. No native work is required to ship — it is a later, low-cost enhancement.

7. Open decisions

  1. Frontend framework — React vs Svelte. Decided: Svelte, for leanness, realtime/overlay fit, gentler DX for a systems-programmer maintainer, tiny bundles, and the lean Tauri/single-binary ethos. The revisitable alternative is React (larger FOSS contributor pool and ecosystem). Recorded as the chosen default and reversible at known/bounded cost — only the component library and surface entry points are framework-specific. (Tracked from Architecture §11.)
  2. Design-system specifics (deferred). The token set, component states, and whether the component library is built on a headless primitive kit or bespoke — deferred to design work, now constrained by the chosen framework (Svelte, §2).
  3. Component-library packaging. Resolved: a monorepo with a shared components package. The race-domain widgets live in one shared package consumed by all surface entry points, with per-surface builds in the same monorepo.
  4. Overlay client conventions. Resolved: fixed canvas + transparent + URL-carried race/class. OBS browser sources render at a fixed canvas size on a transparent background, and an overlay is told which race/class it shows via its URL — coordinated with Streaming, which owns the catalogue and theming.
  5. LAN read access posture. Resolved: open, with an optional signed join-token. LAN reads are open by default, with an optional signed join-token (per Protocol) when an event wants to gate access — pairs with the auth model in Protocol and the trust boundaries in Architecture §9.
  6. Native push details (deferred). When the Capacitor wrap lands, how native push registration maps onto the Cloud push infrastructure — paired with Cloud & Season.
  7. RD mobile-control surface (future). A privileged, mobile-optimized control client exposed LAN-only (§1), reusing the control path (Protocol §5) but requiring stricter authentication than the console (explicit RD login / device pairing). The auth/pairing mechanics and exact mobile control UX are future work; control authority stays Director-only and LAN-only.
