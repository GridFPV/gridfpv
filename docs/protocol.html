Protocol

Internal design doc · the one read/realtime contract every client speaks

The single read/realtime contract. A client opens it, fetches a snapshot of the projections it cares about, then subscribes to a realtime change stream. The Director serves it on the LAN and the Cloud serves the identical contract off-LAN — a client knows only a base URL and can't tell which it's talking to. This doc makes "one protocol, two transports" concrete.

This doc owns the read model (snapshot), the realtime change stream, subscription scoping, auth & authorization, and contract versioning. It deliberately does not redefine the projections themselves — those belong to the engines that derive them (Race Engine, Cloud & Season) — nor the timing vocabulary (Timer Adapters). It defers the cross-event registry and account model to Cloud & Season, and the overlay catalogue to Streaming. Trust boundaries are fixed in Architecture §9; the wire mechanics are decided here. Final calls on WS-vs-SSE, exact message schemas, and the token/session format are left in Open decisions. When this doc and the Vision disagree, the Vision wins.

1. What the protocol serves — projections, not the log

The append-only log is the single source of truth, but it is never the wire format. Clients read projections — the answers derived by folding the log (Architecture §3) — plus live race-state. The raw event log is an internal concern of the Director and the Cloud warehouse; it is exposed only through bulk export / open-data endpoints, not through the realtime contract.

The protocol is a read interface over projections. The Pass atom, the canonical timing events, and the race-state events that drive the heat loop are inputs the Director folds. Clients receive the folded result — a lap list, a heat result, a ranking — never the unfolded observations and adjudications behind it.

The projections the contract serves, each its own addressable resource:

Live race-state
The current heat and its loop state (Scheduled → Staged → Armed → Running → Landed → Scored, see Race Engine §2), the active pilots and their live lap/split progress, the running order, and the on-deck heat. The latency-sensitive core every overlay and spectator watches.
Lap lists
Per-pilot, per-heat laps and splits, already folding marshaling adjudications (void, insert, adjust). What the engine derives, not what the timer reported.
Heat results
The scored outcome of a heat — finishing order, lap counts, the applied win condition and tie-breaks.
Qualifying ranking / seed
The aggregated ordering a qualifying format exposes, including the provisional / partial ranking mid-format and the final seed handed to the mains.
Bracket state
The mains structure — heats, seeds, advancement, the path toward a winner — as the bracket generator currently sees it.
Standings
Event standings derived across a class's phases. (Career and season standings are the same shape but Cloud-only by nature — see Cloud & Season.)
Event & schedule
The framing config a client needs to make sense of the rest: the event, its classes, tracks, heats/rounds, and the pilot/entry roster.

The dividing line restated for the wire: if it's an observation or a decision, it lives in the log and the client never sees it directly; if it's an answer computed from those, it's a projection and the protocol serves it. This keeps the wire contract stable while the log vocabulary and projection internals evolve underneath.

2. The snapshot read model

A client begins by fetching a snapshot: the current materialized state of exactly the projections it cares about, over plain HTTP GET. The snapshot is self-contained and immediately renderable — a spectator who loads the page sees the full current standings before a single live update arrives.

Snapshot first, then subscribe. Every client follows the same two-step handshake: read a snapshot of its scope, then attach the realtime stream to keep it current. The snapshot carries the sequence cursor the client uses to start the stream exactly where the snapshot ended (§3) — so nothing is missed and nothing is double-applied in the gap between the two calls.

Snapshot reads are:

  • Scoped — addressed by resource and filter (a class, a heat, a pilot; see §4), so a phone fetches one heat, not the whole event.
  • Cacheable where they're stable — a scored heat result or a finished event is immutable-until-marshaled and carries cache validators; live race-state is not cached. This is what lets the Cloud's long-term portal scale read-heavy and the live surface stay dynamic (Architecture §8).
  • Paginated for large reads — full event history, multi-event open-data queries, and warehouse browsing page through results; live single-event scopes are small enough to return whole.

Because the Director and the Cloud reuse the same server crate behind a storage trait (Architecture §2), a snapshot computed from SQLite on the LAN and from Postgres in the Cloud is the same shape — the client cannot tell them apart.

3. The realtime change stream

After the snapshot, the client opens a WebSocket and receives a stream of change envelopes that advance its projections. WebSocket is the working default carried over from Architecture §11; SSE is noted below as a read-only fallback.

Snapshot + incremental changes. The stream sends deltas, not repeated full state — a new lap, a heat-state transition, a re-scored result. Each envelope names the projection it touches and carries a monotonically increasing sequence number. The client applies envelopes in order to keep its local copy identical to the server's, and the server may collapse a burst into a single "this projection changed, here's its new value" envelope when a delta would be larger or ambiguous (e.g. after a marshaling correction that re-folds a whole lap list).

Sequence, ordering & resume

The stream carries a projection sequence number — a per-stream counter that increases by one per envelope. It is not the raw log offset: the log is an internal source of truth (§1), and one log append can fan out into several projection changes (or none a client subscribes to). The protocol commits to the projection sequence as its public ordering; the log offset stays a private implementation detail the Director and Cloud use for their own resumable sync (Architecture §3).

Resume by cursor, fall back to re-snapshot. The snapshot hands the client a starting sequence cursor; every envelope advances it. On a dropped connection the client reconnects and presents its last-applied cursor. If the server can still serve the gap, it replays the missed envelopes and the client is seamlessly current. If the gap is too old to replay (beyond the retained window), the server tells the client to re-snapshot — fetch a fresh snapshot and resume the stream from its new cursor. Re-snapshot is always correct because projections are recomputable; the stream is an optimization, never the source of truth.

Ordering guarantees, stated plainly:

  • Total order per stream. Within one subscription, envelopes arrive in strictly increasing sequence; a client that applies them in order converges to the server's state.
  • No gaps without notice. A client detecting a sequence jump it can't bridge must re-snapshot rather than render a hole.
  • Idempotent application. Re-delivering an envelope the client already applied (after a flaky reconnect) is a no-op, keyed by sequence — so resume can safely overlap.
  • At-least-once, deduplicated. The transport may redeliver; the sequence makes that harmless. The protocol does not promise exactly-once delivery, only exactly-once effect.

SSE as a read-only fallback

Spectators and overlays are pure readers — they never send anything up the socket. For them a one-way Server-Sent Events stream would carry the same change envelopes over plain HTTP, with the browser's built-in Last-Event-ID reconnect mapping naturally onto the sequence cursor. The cost is a second code path and a separate story for the RD console, which genuinely needs a bidirectional channel for control (§5). Whether SSE earns its keep as a read-only fallback, or whether one WebSocket transport should serve every client, is an Open decision — but the envelope shape is designed to be transport-neutral so either can carry it.

4. Subscription scoping

A subscription is a scope plus a starting cursor. Scope is how a client asks for exactly the projections it needs — both to keep payloads small and to bound what a given client is allowed to see and how often it changes.

Event scope
Everything for one event — the broad default for the Cloud live surface and the "whole venue screen."
Class scope
One class's phases, schedule, and standings — a class running in parallel with others (Race Engine §5).
Heat scope
One heat's live race-state and lap lists — the tightest, lowest-latency scope, ideal for a phone watching the current heat or a leaderboard overlay.
Pilot scope
One pilot across the event — a racer following their own laps, results, and next heat.

Scopes compose (a pilot within a class) and a client may hold several at once over one connection. The three client kinds differ in scope and permission:

Overlays and spectators are read-only and look identical on the wire to the read half of the RD console — only the RD console additionally holds the privileged control channel. This is exactly the architecture's claim that overlays and the racer PWA are "the same kind of thing, differing only in transport and permission" (Architecture §5, §10).

5. Auth & authorization

Access splits into read and control, following the trust boundaries fixed in Architecture §9. This doc decides only the wire mechanics.

Reads are open (or lightly tokened) on the LAN. Anyone on the venue LAN can fetch snapshots and subscribe to the read stream — that's the point of a local spectator/overlay experience with no internet. An optional lightweight join token (printed as a QR code, baked into the URL) can gate casual access to the event without standing up accounts; it grants read scope only and never confers control.

Control is authenticated and Director-local. Race control, marshaling, and configuration require the RD's authenticated role and run only against the Director. The control path is a distinct, privileged set of endpoints / a privileged channel on the same connection — bidirectional by nature (commands up, acknowledgements and resulting state down), which is part of why the RD console wants WebSocket regardless of the spectator-transport decision.

Future: the control path may serve one or more authenticated RD-role clients on the LAN — the desktop RD console and/or a future mobile RD-control surface the RD uses to run the race from their phone (e.g. start the heat from their seat). It still requires the RD role (with stricter auth for a mobile device) and, like all control, is Director-only and never exposed on the Cloud.

The Cloud authenticates accounts but never controls. Off-LAN viewers reach the Cloud with accounts; the Cloud serves the identical read contract and relays. It exposes no control path at all — control authority never leaves the Director (Architecture §9). An RD does not run a race "through the Cloud"; the Cloud only ever reflects what the Director already decided.

Same read contract, different gate. The read half of the protocol is byte-identical on both transports; only what stands in front of it differs — open / join-token on the LAN, account auth on the Cloud. Because the storage trait makes the server crate identical on both sides, "authorize this read" is a thin policy layer, not a fork of the contract. The exact token/session format (opaque token, signed JWT, cookie session) is deliberately left open below.

IRLThe control path is exercised constantly — staging, frequency assignment, marshaling rulings, re-runs — all from the authenticated RD console.

SimSame control path, lighter use — mostly start/abort and discard-and-re-run; no frequency or signal marshaling.

6. The contract defined once, in Rust

The wire types — snapshot bodies, the change envelope, scope and subscription requests, control commands and their acknowledgements, error shapes — are defined once, as Rust types in the server crate, and generated into TypeScript (e.g. ts-rs) for the frontend (Architecture §2, §6).

One definition, no drift. The Director, the Cloud relay, and every client — RD console, spectator PWA, overlays — consume the same generated types. There is no second hand-maintained schema to fall out of sync, and a breaking change to a wire type is a compile error on the Rust side and a type error on the TS side before it is ever a runtime bug.

The same crate reuse that gives the Cloud the identical contract (Architecture §2) gives type generation for free: the types are a property of the shared crate, not of either deployment. Type generation runs as a build step that emits the TS module the frontend imports; keeping it offline and reproducible is part of the build story (deferred to the Roadmap).

7. Versioning & evolution

Three independently-updated parties must stay compatible: an older PWA a spectator hasn't refreshed, a newer Director the RD just upgraded, and a Cloud relay on its own deploy cadence. The contract is built to evolve without lockstep upgrades.

Additive by default; breaking changes are explicit. New projections, new fields, and new envelope kinds are added so that an older client safely ignores what it doesn't understand and a newer client treats absent fields as absent. A genuinely breaking change (a removed field, a changed meaning) requires a new contract version, never a silent reinterpretation.

The contract version is negotiated, not assumed. A client announces the contract version it was built against at connect time; the server states the version(s) it serves. A server supports a band of recent versions so an un-refreshed PWA keeps working; when a client is too old to be served, it gets a clear "please refresh" signal rather than malformed data. The negotiated version is independent of the transport (LAN or Cloud) and of the underlying log/schema version.

Three version axes, kept distinct. (1) The contract version — the wire shapes, owned here. (2) The log / schema version — how the append-only event format evolves while keeping old events readable for long-term open data (Architecture §11). (3) The projection version — the internal derivation logic, which can change freely as long as the contract output is unchanged, because projections are recomputable. The protocol pins only axis 1; it must stay decoupled from 2 and 3 so the Director can recompute and re-derive without forcing a client upgrade.

8. End-to-end shape

Putting it together: the Director folds the log into projections and serves them through the one contract on the LAN; the Cloud reflects the same contract off-LAN from the warehouse; every client does snapshot-then-subscribe and can't tell the two apart.

9. Open decisions

  1. RESOLVED — Realtime transport: WebSocket-only first. WebSocket is the working default (Architecture §11) and the RD control path needs it regardless, so the contract ships WebSocket-only for every client. The change envelope stays transport-neutral, so an SSE read-only path can be added later only if a real spectator/overlay need appears — not by default, to avoid a second code path.
  2. RESOLVED (accepted as working design) — Change-envelope schema: delta vs fresh-value, per projection. The accepted approach is deltas for append-heavy projections (lap lists, live state) and fresh-value for cheap or re-folded ones (heat result, ranking after a correction), with a marshaling re-fold surfacing as a fresh-value envelope. The exact envelope shapes are refined at implementation.
  3. RESOLVED (accepted as working design) — Resume window & retention. The server retains a bounded window of replayable envelopes before forcing a re-snapshot: the Director is memory-bounded (one event) and the Cloud keeps a larger window (many events). Pairs with the storage tiers in Architecture §4. Exact window sizes are tuned at implementation.
  4. RESOLVED — Auth credential format: opaque bearer tokens (+ optional signed join-token). RD and account auth use opaque bearer tokens backed by a server-side session (easy to revoke), plus an optional lightweight signed join-token (printed as a QR code, baked into the URL) granting read-only LAN access. Trust boundaries are fixed in Architecture §9. Revisit JWT only if stateless Cloud scaling later demands it.
  5. RESOLVED (accepted as working design) — Sequence-cursor representation. The public projection sequence is a single monotonic integer per stream (not per-projection cursors a client composes). How it stays stable across a Director restart / projection recompute is settled at implementation.
  6. RESOLVED (accepted as working design) — Scope grammar & pagination. The contract uses a scope grammar for addressing (with multi-scope subscribe) and cursor-based pagination for large historical / open-data reads. The exact addressing scheme, URL shapes, and filter expressiveness are refined at implementation.
  7. RESOLVED (accepted as working design) — Contract version negotiation & support band. The version is carried in the connect message; the server serves a band of recent versions so an un-refreshed PWA keeps working, and emits an explicit "too old, please refresh" signal when a client falls outside it. Paired with log/schema versioning in Architecture §11. The exact support-band depth is set at implementation.
  8. RESOLVED (accepted as working design) — Error model. The contract uses a single shared error shape across HTTP reads, the WS stream, and control acknowledgements — auth failure, unknown scope, stale-cursor, version-mismatch — defined once in Rust like the rest of the contract. The exact fields are pinned at implementation.
