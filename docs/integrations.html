GridFPV

External Integrations

Internal design doc · the outside world — MultiGP, imports, open data, secrets

Everything that crosses the boundary between GridFPV and another system: MultiGP RaceSync (roster in, results out), the leaderboard / roster imports that seed an event, the open-data surfaces a pilot's data flows out through, and the credentials all of that needs. Every one of these is internet-dependent, reads derived projections rather than raw timing truth, and lives outside the live critical path of a race.

This doc owns the external boundary: the RaceSync integration, the ingestion path for imports, the open-data read API / export / widgets, and Director-side credential handling. It defers the wire contract these surfaces reuse (Protocol), the warehouse and the long-term portal that hosts the public dashboards (Cloud & Season), the canonical timing model imports deliberately bypass (Timer Adapters), and where imports plug into setup and qualifying (Event Pipeline). Cloud-specific secrets and deployment config are out of the FOSS repo entirely. When this doc and the Vision disagree, the Vision wins.

1. The shared shape of integrations

MultiGP sync, leaderboard imports, and the open-data API look like different features, but architecturally they are the same kind of thing: a translator that sits between an external system and GridFPV's internal truth, on the network side of the wall. Three stances apply to all of them, and they follow directly from the Architecture (Architecture §5, External sync).

Never in the live critical path. A race runs end to end with zero internet. Every integration here is allowed to be slow, retried, queued, or entirely absent without degrading anything that happens on the timing floor. If MultiGP is unreachable, the heat still fires; the push simply waits.

Reads projections, never raw truth. What flows out — results to RaceSync, rows from the open-data API — is read from the derived projections (heat results, the qualifying ranking, standings, career stats), not from the append-only log directly. The log is the source of truth; integrations consume the answers computed from it. Because any projection is recomputable, a re-push or a re-query always reflects current truth, including after a marshaling correction.

Internet-dependent and bidirectional, but asymmetric. Outbound (results push, open-data serving) and inbound (roster / leaderboard import) are both gated on connectivity, but they touch GridFPV differently: imports ingest into event configuration, results / open-data read from projections. Neither ever writes the timing log.

2. MultiGP RaceSync

First-class RaceSync integration is a non-negotiable Vision pillar for US chapter racing (Vision §1). It has two halves — pulling a chapter's roster in at setup, and pushing the event's results back out — bracketing a chapter registration to the official record without retyping anything.

Chapter authentication

RaceSync is organized around chapters. To act on a chapter's behalf — read its roster, push its results — the Director authenticates with a chapter-scoped API key the RD supplies once and GridFPV stores locally (see §5). Authentication is a setup-time, internet-dependent step; it is never required to run a race, only to sync with MultiGP.

Authenticate the chapter, not the pilot. The credential authorizes GridFPV to operate on one chapter's events and roster. Individual pilots are identified within that chapter (e.g. by their MultiGP pilot id), but the trust boundary is the chapter key the RD holds — consistent with the Director being the authoritative operator of the event.

Roster import at setup

At Setup & Registration (Event Pipeline, Phase 1) the RD can pull the chapter roster from RaceSync to assemble the field without manual entry. This is an import / ingestion, covered in §3 — it produces GridFPV entries and a pilot-id mapping, not live passes. The same mapping is what lets the results push later address pilots by their MultiGP identity.

Pushing results — during and after the event

The headline capability: send pilots, heats, lap times, and placements back to RaceSync so the chapter's official record matches what was flown. Because the push reads projections, it can run incrementally during the event (each heat / round as it finalizes) and as a final reconciling push after, and it never blocks the race that produces the data.

The push is a queued, resumable projection mirror. Pushes are enqueued as projections finalize and drained whenever the internet is up; a drop pauses the queue and resumes it, no race-day intervention. Because projections are recomputable and the target is addressed idempotently (this heat, this pilot, this round), a re-push after a correction overwrites rather than duplicates — the same property the Cloud's resumable log push relies on (Architecture §3), applied to a results mirror instead of the raw log.

IRLThe mainline case — a sanctioned MultiGP chapter race pushing official results, lap times, and bracket placements to RaceSync.

SimRaceSync push is generally not applicable to a pure Velocidrone event; where a chapter runs sim racing under its banner the same mechanism applies, but the common sim integration is the leaderboard import (§3), not the push.

Reuse over reinvention: RotorHazard's RaceSync plugin is prior art for the same conversation with MultiGP. The exact RaceSync API surface we depend on — endpoints, auth flow, and the result payload shapes for heats / laps / placements — is captured as an Open decision (§6) and pinned against the live API when the integration is built, the same discipline the adapter docs apply to external schemas.

3. Imports are ingestion — not timer adapters

Two imports matter first (neither built yet, as of v0.4.0-alpha.1): the MultiGP chapter roster (at setup) and the Velocidrone leaderboard (for qualifying seeding). Both bring data in from outside, and both deliberately live here / with qualifying — not in the timer-adapter layer.

Imports produce rosters and rankings, not live passes. A timing adapter emits the canonical Pass — a live observation that the engine derives laps from. An import emits no observations at all: a roster import yields entries, a leaderboard import yields a seed ranking. They populate configuration and projections, never the timing log. That is precisely why Timer Adapters declares leaderboard / results imports out of scope — the adapter layer is live timing sources only.

The MultiGP chapter roster (setup ingestion)

Pulls the chapter's pilots from RaceSync and turns them into event entries, carrying each pilot's MultiGP id so the later results push (§2) and any cross-event identity reconciliation (Cloud & Season) can address the right person. It feeds the same registration machinery as adding pilots by hand or letting them self-register — it is just a faster way to assemble the field.

The Velocidrone leaderboard (qualifying ingestion)

In sim racing the leaderboard for a spec track is the qualifying ranking — "leaderboard bashing" (Event Pipeline, Phase 3). Importing it produces the ordered seed that the mains build from, treated as an equal to running qualifying live or skipping it. It is a ranking, full stop: no per-pass timing, no signal context, nothing the adapter model would carry.

SimOne-click leaderboard import is the intended path — pilots grind a track, the leaderboard becomes the seed.

IRLThe roster import is the common case; a results-derived ranking (e.g. seeding from prior MultiGP results) is the IRL analogue of importing a ranking rather than flying qualifying.

Why the split matters: keeping imports out of the adapter layer keeps that layer's one job honest — translate live sources into canonical observations and nothing else (Timer Adapters §1). Ingestion is a different shape of data with a different destination (config / rankings), so it earns a different home: here for the network mechanics, with Qualifying / Setup for where it plugs into the pipeline.

Roster import
External source (MultiGP chapter, Velocidrone room) → a set of event entries plus a local-ref / external-id mapping. Setup-time. Feeds registration, not the log.
Ranking import
External leaderboard / results → an ordered seed ranking for the mains. Qualifying-time. A projection input, not live passes.
Results push (outbound)
The inverse direction — GridFPV projections → RaceSync. Covered in §2; listed here to complete the boundary's data flows.

4. Open data

Open data is the core differentiator versus closed platforms: a pilot's racing history belongs to the pilot, and GridFPV exposes it rather than hoarding it (Vision §4). Three surfaces, all reads of projections over the truth in the append-only log.

Public read API
A queryable HTTP surface over derived projections — event results, standings, and (in the Cloud) career profiles, head-to-head records, per-track personal bests, season standings. Read-only; it never exposes a control or write path.
Data export
A pilot or chapter takes its data out wholesale. The per-event SQLite file already is the export (Architecture §3) — the unit of truth, portable and replayable; the open-data surface adds friendlier projected exports (e.g. results / laps as structured rows) on top.
Embeddable widgets
Drop-in components a chapter can put on its own site — live leaderboards, standings, pilot cards — reading the same public projections so chapters build their own dashboards and ranking sites on GridFPV's open data.

Open data is the read contract, pointed at the public. The public API is the same kind of thing as the racer/spectator read surface — a read of projections — so it reuses the one read/realtime contract rather than inventing a second one (Protocol). The differences are reach (public, internet) and shape (large historical / cross-event queries, pagination, caching), not a separate protocol. The contract is built once and honored here too.

Recomputable means trustworthy. Because every public metric is a projection over an append-only log, any figure can be recomputed over the full history, and a new metric is a new projection — not a migration. Openness is durable: what we expose can always be re-derived and re-served, including after corrections.

Open to any account-holder, not anonymous. Open data is open in the sense that any pilot or chapter can get the full, queryable, exportable data and keep their own portable copy — not in the sense that Cloud reads are unauthenticated. The Cloud open-data API and export require a free account / account-anchored API key rather than anonymous access; the gate is an account, not a paywall, and a pilot's data stays portable to them. The Director still serves single-event open data openly on the LAN — it is offline-first, where no Cloud account is even possible. Public embeddable widgets are a per-chapter opt-in: a chapter may choose to publish a public widget for its events.

Where it lives: single-event open data can be served openly by the Director on the LAN, but the cross-event surface — career profiles, season standings, the dashboards chapters embed — is Cloud-only by nature, because only the Cloud warehouse holds the accumulated history (Architecture §8; Cloud & Season), and Cloud reads are account-gated (a free account, anchored to an API key). The Cloud reuses the same Rust server crate over Postgres, so the public read surface is one contract served from either tier — the long-term portal is just its widest, most-cached deployment.

5. Credential & secret handling

External services need credentials — most concretely the MultiGP chapter API key. These are Director-side, internet-dependent, and held only to talk to the outside; they are never needed to run a race.

Secrets are Director-side and off the wire contract. A chapter API key is stored with the Director's local configuration (the catalog tier, Architecture §4), used only by the outbound integration code, and never placed in the append-only log, a projection, the read contract, or any export. The log stays a clean, shareable record of the race; a secret never leaks into open data.

Cloud secrets are out of the FOSS repo. Anything the optional Cloud needs — its own service credentials, deployment config, signing keys — lives with the Cloud deployment, not in the open-source repository. The FOSS Director carries only the credentials an RD supplies for their own event (the chapter key); the Director's single-event open data is served openly on the LAN with no secret at all, while Cloud open-data reads use the reader's own free account / account-anchored API key rather than any secret of ours.

The concrete mechanics — how a key is entered, where it is stored on disk, whether it is encrypted at rest or scoped per chapter, and how multiple chapter keys coexist — are an Open decision (§6). The fixed commitment here is the boundary: secrets are Director-local, used only for outbound sync, and never enter the log, projections, the read contract, or any export.

6. Open decisions

  1. Exact RaceSync API scope. The specific endpoints, auth flow, and result payload shapes (heats, lap times, placements) GridFPV depends on, plus incremental-vs-final push granularity and idempotency keys. Accepted as recommended: pin the RaceSync API scope against the live API at build time, using RotorHazard's RaceSync plugin as prior art; treat a sanctioned chapter event as the validation case rather than mocking the API blind. Open refinement: the exact endpoint list and payload shapes still get fixed when the integration is built.
  2. Open-data API shape & auth. Whether the public read API is exactly the protocol's read contract or a thinner public projection of it; query / pagination model for large historical and cross-event reads; and rate-limiting. Decided (auth): Cloud open-data reads are account-gated — they require a free account / account-anchored API key, not anonymous access — while the Director serves single-event open data openly on the LAN; data stays open to any account-holder and portable to the pilot. Recommendation (shape): reuse the one read contract (Protocol), adding only pagination and caching for the cross-event scale; settle the remaining shape questions alongside the Protocol auth/scoping decisions.
  3. Widget embedding model. How embeddable widgets are delivered and isolated — iframe vs web component vs script snippet — and how a chapter scopes a widget to its events / pilots. Decided (publishing): public widgets are a per-chapter opt-in — a chapter chooses whether to publish a public widget at all. Recommendation (delivery): favor a self-contained embed (iframe or web component) that talks only to the public read API, so a chapter never handles a credential to embed; decide the remaining delivery details with the long-term portal in Cloud & Season.
  4. Credential storage mechanics. Where the chapter API key is stored, encryption at rest, per-chapter scoping, and handling multiple chapter keys on one Director. Accepted as recommended: store the chapter API key in the Director catalog tier with at-rest protection via the OS keystore, scoped per chapter, and keep it strictly out of the log and every export. Open refinement: handling multiple chapter keys on one Director and the keystore fallback where none is available.
  5. Sync trigger & queue policy. What drives the results push (per-heat finalize, per-round, manual, periodic), how the outbound queue retries and surfaces failures to the RD, and how a re-push after a correction reconciles. Accepted as recommended: automatic per-round enqueue plus a manual "push now" and a visible, resumable queue — never a blocking, in-the-critical-path call. Open refinement: retry backoff and exactly how failures surface to the RD.
  6. Import provenance & refresh. Whether an imported roster / ranking records its source for re-import, and how a re-import reconciles with entries the RD has since edited (added pilots, manual seed changes). Accepted as recommended: tag imported entries with their source and re-import as a non-clobbering merge that preserves local RD edits. Open refinement: the exact conflict rule when a re-imported entry diverges from a hand-edited one.
