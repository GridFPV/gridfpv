Streaming

Internal design doc · the broadcast subsystem · draft

Integrated broadcast: the overlays that visualize a live race, and the Director-side subsystem that drives OBS and handles capture / RTMP inputs — on par with the streaming benchmark, but open and driven directly by live race state.

Early draft. This page captures scope and the open decisions routed here from the Architecture doc (see §10), so they're tracked in the right place. The subsystem itself is not yet specified. When this doc and the Vision disagree, the Vision wins.

Scope

The architecture fixes two commitments this doc builds on:

  • Overlays are protocol clients. Staging, leaderboard, split-screen, podium, and bracket overlays are web pages driven by the same read/realtime contract as every other client, loaded as OBS browser sources — no special path.
  • Broadcast control is an optional Director subsystem. Driving OBS and handling capture / RTMP is active output the Director performs, reacting to live state, but never in the timing critical path.

This doc will own the design of:

  • The OBS control model — connecting to OBS and mapping race events to scene/source changes.
  • Capture / RTMP handling — what video the Director ingests or relays, vs. what it leaves to OBS.
  • The overlay catalogue — the set of overlays, their data needs, theming, and chapter branding.

Open decisions

  1. OBS control model. Use the obs-websocket API; decide which transitions are automatic (driven by race-state events) vs. RD-manual, and how scene mappings are configured.
  2. Capture / RTMP boundary. Whether the Director ingests video / accepts RTMP inputs itself, or strictly controls OBS and leaves all video to it — the architectural line between GridFPV and the streaming stack.
  3. How overlays receive data. Confirm overlays subscribe to the protocol like any client (consistent with Architecture §6), rather than a bespoke push — and how an overlay is told which race / class it is showing.
  4. Overlay catalogue & theming. The initial set of overlays, customization, and chapter branding.
  5. Multi-class / multi-output. Driving multiple scenes or outputs when classes run concurrently.
