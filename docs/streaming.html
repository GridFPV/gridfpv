Streaming

Internal design doc · the broadcast subsystem — overlays, OBS control, and the capture boundary

Integrated broadcast, built the same way as everything else: overlays are ordinary clients of the one protocol, and the thing that drives OBS is an optional Director subsystem that consumes race-state — never a dependency of timing. This doc owns the broadcast side: how overlays are told what to show, how race-state events map to scene switches, and exactly where GridFPV stops and the streaming stack begins.

This doc owns the broadcast subsystem: overlays as broadcast surfaces, the OBS control model, the capture / RTMP boundary, and the overlay catalogue & theming. The client/rendering side of overlays — how a web page subscribes to the protocol, renders projections, and reconnects — is a client surface like any other and is owned by Clients; this doc cross-links there rather than re-specifying it. Live capture cards, encoding, RTMP ingest, and the stream itself are out of scope — they belong to OBS and the streaming platform, by design (§4). It builds on Architecture §10 (Streaming & broadcast) and §6 (one protocol), and the race-state events from Race Engine §2. When this doc and the Vision disagree, the Vision wins.

1. The principle

Integrated streaming is a stated Vision goal, but it earns its keep only if it never compromises the thing the Director exists to do — run a race correctly, offline. So the whole subsystem is built around one hard line.

Broadcast is never in the timing critical path. Overlays and OBS control are readers of live state. If OBS is closed, the overlay browser crashes, or the broadcast operator unplugs everything, the race runs exactly as it would have. Timing, scoring, and advancement do not know or care that anyone is streaming.

Two halves, drawn from Architecture §10. One half we get for free: overlays are protocol clients — live race state already flows to them, no special path. The other half is a genuine subsystem: broadcast control, which actively drives OBS in reaction to race-state events. The free half needs no new infrastructure; the active half is optional and isolated.

Same contract, nothing bespoke. Overlays subscribe to the same read/realtime contract as the RD console and the racer PWA (Architecture §6). There is no overlay-only push channel, no privileged firehose — an overlay is a read-only client that happens to render full-screen on a transparent background. That is what lets a community theme its own overlays without touching the Director.

2. Overlays as protocol clients

An overlay is a web page — staging grid, leaderboard, split-screen lower-thirds, podium, bracket tree — served by the same embedded server that serves every other client, and loaded into OBS as a browser source. It opens the protocol, fetches a snapshot of the projections it needs, subscribes to the realtime change stream, and paints. The rendering, reconnect, and snapshot-then-subscribe mechanics are identical to any client and are specified in Clients; what matters here is the broadcast framing around them.

2.1 How an overlay is told what to show

A leaderboard browser source needs to know which race and which class it is showing — and when several classes run concurrently (§6), two leaderboard sources in different OBS scenes must show different classes. Because an overlay is a plain web client, the answer is a plain web answer: the target is carried in the URL.

Explicit binding
The browser-source URL names exactly what to show, e.g. /overlay/leaderboard?class=mini&heat=current. The overlay subscribes to that class's projection and renders it. Two scenes, two URLs, two classes — no coordination needed. This is the unambiguous default for multi-output.
Follow-the-program
The URL asks for "whatever is on air," e.g. /overlay/leaderboard?follow=program. The overlay tracks the currently-featured race/class (a small piece of broadcast state the server publishes, §3.3) and re-binds itself as the program changes — convenient for a single-class event or a manually-operated single-output show.
Selector overlays
Some overlays (a full bracket tree, an event schedule) are inherently event-scoped rather than heat-scoped and only need the event id; they render the same regardless of which heat is live.

Why URL-carried binding, not a control message: it keeps overlays stateless and trivially reproducible — paste the URL into OBS and it works, on any machine on the LAN, with no setup handshake. It also means a broadcast operator can hand-author scenes without GridFPV knowing those scenes exist. The "follow-the-program" mode is the only place an overlay reads broadcast state, and even then it is reading a published projection, not receiving a private push.

2.2 Where overlays run

Overlays are browser sources, so they obey the same transport rules as any client (Architecture §6): on the LAN they hit the Director directly; off-LAN (a remote commentator's OBS) they hit the Cloud relay with the identical contract. The broadcast machine does not have to be the Director machine — it just needs to reach one of the two transports.

IRLThe broadcast PC is usually a second machine fed by capture cards and VTX receivers; overlays point at the Director over the venue LAN.

SimEverything can live on one box — Velocidrone, the Director, OBS, and the overlays — so overlays often point at localhost, and the sim's own clean video is the program feed rather than a capture card.

3. Broadcast control — the optional subsystem

Broadcast control is the active half: a Director subsystem that connects to OBS and switches scenes and sources in reaction to race-state events, so the stream follows the race without a human riding the switcher. It is optional, isolated, and — to restate the guardrail — it consumes projections and race-state and never feeds anything back toward timing.

3.1 How it connects

The subsystem is a client of obs-websocket (the standard OBS Studio WebSocket API). The RD configures a host, port, and password; the Director connects as a controller. This is a deliberately conventional integration — obs-websocket is the de facto standard control surface for OBS, and using it means GridFPV drives any OBS the operator already runs rather than shipping its own switcher.

Broadcast control reads race-state, drives OBS. Internally it is the mirror image of a timer adapter: where an adapter translates a source's input into canonical events, broadcast control translates race-state events out into OBS commands. It owns no truth and appends nothing to the log — it is a pure consumer.

3.2 Mapping race-state to scenes

The heat loop already appends the events broadcast wants (Race Engine §2): staged, armed, started (running), landed, scored, advance. A scene map associates phases of that lifecycle with OBS scenes; as race-state changes, the subsystem requests the mapped scene.

Race-state eventTypical broadcast intentDefault mapping
stagedfield is on the line; show who's upStaging / grid scene
armedcountdown imminent(hold staging, arm lower-third)
started (running)race is liveRace / split-screen scene
landedflying done, result pending(hold race, results lower-third)
scoredresult is finalResults / replay scene
advancemoving to next heat / podiumBracket or podium scene

The map is data, not code: a per-event (overridable per-class) table of phase → scene name, edited in the RD console and stored as event configuration in the log (Architecture §4) so the broadcast setup travels with the event and is reproducible. Scene names are the operator's; GridFPV references them by name and reports clearly when a mapped scene is missing in OBS rather than guessing.

3.3 Automatic vs RD-manual transitions

Not every cut should be automatic — a producer often wants to linger on a crash, cut to a pit interview, or roll a replay before advancing. So transitions come in three modes, chosen per mapping:

Automatic
The race-state event triggers the scene switch directly. Good for the predictable backbone (staged → race → results) and for unattended sim streams.
Armed / one-touch
The event arms the next scene and surfaces a prompt in the RD console (or a broadcast-operator view); a human confirms the cut. The race never waits on the confirmation — it has already advanced; only the picture is held.
Manual
GridFPV makes no automatic switch; the operator drives OBS as usual. The subsystem can still feed overlays and publish "what's on air" for follow-the-program overlays.

The program pointer. Whatever drives the cut, the subsystem maintains and publishes a small piece of broadcast state — the currently-featured race/class — as an ordinary projection on the protocol. That is what follow=program overlays (§2.1) read, and it is the one bit of broadcast state worth making first-class. It is derived from race-state plus operator action; it is not authoritative over anything and is recomputable/disposable.

4. The capture / RTMP boundary

This is the most important line in the doc: where GridFPV ends and the streaming stack begins. The Vision wants integrated streaming, but "integrated" means orchestrated, not reimplemented.

OBS owns video; GridFPV owns data and direction. Capture cards, VTX receivers, webcams, encoding, RTMP/SRT ingest, recording, and the outbound stream to YouTube/Twitch are OBS's job. GridFPV contributes the data layer (overlays) and the direction layer (scene switching by race-state). It does not become a video pipeline.

ConcernOwnerNotes
Capture cards / VTX receivers / webcamsOBSconfigured as OBS sources; GridFPV never touches the hardware
Video encoding & the outbound stream (RTMP/SRT to platform)OBSGridFPV may start/stop the output via obs-websocket, but does not encode or push pixels
Scene / source compositionOBS (authored) + GridFPV (switched)operator builds scenes; GridFPV selects among them by race-state
Overlays (data graphics)GridFPVserved as browser sources; pure protocol clients
Scene-switch directionGridFPV (broadcast control)optional; obs-websocket; never in timing path
Recording / replay bufferOBSGridFPV may trigger the OBS replay buffer on a scoring event; it does not store video

Why not ingest video ourselves? A Rust media pipeline (RTMP server, transcoding, compositing) is an enormous, latency-sensitive, platform-specific surface — exactly the kind of thing that could threaten "it cannot crash mid-heat" (Architecture §2) if it shared a process with timing. OBS already does it superbly and every FPV broadcaster already runs it. So the strong recommended boundary is control-only: GridFPV speaks obs-websocket and serves browser sources, and no video bytes flow through the Director. Whether GridFPV ever ingests or relays any video (e.g. a convenience RTMP relay) is left as an open decision (§7) — but the default and the architectural preference is that it does not.

5. Overlay catalogue & theming

The initial catalogue covers the standard race-broadcast surfaces. Each is just a protocol client reading specific projections; the broadcast-relevant note is what each needs to be told (its binding, §2.1) and which race-state it reacts to.

Staging grid
Who is up, channels/seats, and the countdown. Heat-bound; reacts to staged/armed.
Leaderboard
Live standings or in-heat positions and lap counts for one class. Heat- or class-bound; the workhorse, driven by the live standings projection.
Split-screen / lower-thirds
Per-pilot name, position, last/best lap as compact strips composited over flight video. Heat-bound; reacts to running passes.
Podium / results
Final placings for a heat or a completed format. Heat- or event-bound; reacts to scored/advance.
Bracket
The mains tree with seeds advancing, or a qualifying ranking. Event/class-bound; reacts to advance and updated standings.

Each gets a fuller spec as it is built; the list confirms the protocol exposes what they need.

5.1 Theming & chapter branding

Theming is presentation, never data. Overlays render from the protocol's projections; a theme changes colors, fonts, logos, and layout — not the numbers. So a chapter can fully re-skin (or replace) overlays without forking the Director, because the data contract is stable and separate from the look.

A theme is a named bundle — palette, typography, logo/wordmark, sponsor slots, and per-overlay layout choices — applied to the catalogue. Chapter branding is a theme plus event-level assets (the chapter logo, the event title card) carried as event configuration so the right branding loads with the event. Because overlays must work offline over the LAN like every other client, theme assets are served by the Director (vendored with the event), with no CDN dependency — consistent with the offline-first stance. The exact theme format and how custom community overlays register against the catalogue is an open decision (§7).

6. Multi-class / multi-output

Several classes can be live at once (Race Engine §5 interleaves heats across classes), and a serious broadcast may run more than one output — a main program plus a class-specific feed, or per-class recordings. The design handles this without any new mechanism, purely by composition.

  • Per-class overlays are just explicitly-bound overlays (§2.1): a browser source per class with class=… in its URL. Two leaderboards for two classes are two URLs in two scenes — nothing coordinates them.
  • Per-class scene maps let each class's race-state drive its own scene set (§3.2), so concurrent classes don't fight over one scene. The default map is per-event; a class override is the multi-class case.
  • Multiple outputs are an OBS concern (multiple outputs / multiple OBS instances / canvas outputs), consistent with the §4 boundary. GridFPV can drive more than one OBS connection — one per output — each with its own scene map; it does not multiplex video itself.

The honesty test: two sim classes running back-to-back on one box, each with its own leaderboard and its own scene, on a single OBS — and the same model scaling up to two physical classes on two OBS instances on two machines. Because every piece is an independently-bound client or an independent OBS connection, concurrency is configuration, not a special code path. How many concurrent OBS connections / outputs to support, and whether per-class is the right granularity, is parked in §7.

7. Open decisions

  1. OBS control model — automatic vs manual surface. Confirmed: drive OBS via obs-websocket, with a per-mapping automatic / armed / manual mode (§3.3). Still open: the exact scene-map schema, whether a dedicated broadcast-operator view is worth building separate from the RD console, and how much of the obs-websocket surface to use (scene switch only, vs also start/stop output, replay buffer, source toggles). Recommendation: ship scene-switching first with a small fixed verb set (set scene, start/stop stream, save replay buffer); expand only as real shows demand it.
  2. Capture / RTMP boundary. Confirmed direction: control-only — OBS owns all video, GridFPV serves overlays and drives OBS (§4). Still open: whether GridFPV ever offers a convenience video path at all (e.g. a thin RTMP relay or a "record this pilot's feed" trigger) or stays strictly control-plane. Recommendation: stay strictly control-plane for v1; revisit only if a concrete need appears that OBS genuinely can't cover, and even then keep any media work in a separate process so it can never threaten timing.
  3. Overlay binding & the program pointer. Confirmed: URL-carried explicit binding is the default; follow=program reads a published broadcast-state projection (§2.1, §3.3). Still open: the exact query-param vocabulary and whether the program pointer is one global value or one per output.
  4. Theme format & custom overlays. The concrete theme bundle format (tokens, layout config, asset packaging), how chapter branding is stored with the event, and how a community-authored overlay registers against the catalogue while staying a pure protocol client. Pairs with the client/rendering details in Clients.
  5. Multi-output granularity. How many concurrent OBS connections / outputs to support, whether per-class is the right unit, and how scene maps are scoped when classes and outputs multiply (§6).
  6. Off-LAN broadcast. Whether the broadcast-control subsystem and remote overlays are expected to operate against the Cloud transport (remote commentary / remote producer), and any added latency or auth implications — ties to the Cloud relay in Cloud & Season and the trust model in Architecture §9.
